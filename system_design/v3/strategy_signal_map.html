StrategySignal

The slot's signal: a DAG of calculations built in Python by a SignalDag subclass, and the entry and exit logic over them. It is pure — bars and position data in, answers out — so it can be tested alone, one bar at a time.

v3 draft, 2026-11-06 — not agreed. A signal is a SignalDag subclass: typed params it holds itself, and a DAG of registered calculations it builds in code, behind an abstract interface. Behaviours 1–5 and decisions 1–4 are settled; behaviour 6, the interface and decisions 5–9 are proposed.

The interface gains entry_conditions(), exit_condition_names(), condition_names() and values() (decision 8). Calculation names are scoped per strategy folder (System map decision 43).

2026-11-06 — First v3 draft. The boundary was fixed and the way a signal is written was left open.

StrategySignal · Goal

Goal

Turn a stream of bars (plus the position data Strategy passes in) into deterministic entry and exit answers: the same signal class and the same bars always give the same answers. Report when it has enough history to be trusted, and be able to rebuild itself from scratch.

Owns, from the System map:

The slot's signal: its calculation DAG and params, stepping the calculations on each bar in dependency order, evaluating the entry and exit logic, reporting whether it is warm, and how to rebuild itself cold by replaying seed bars.

StrategySignal · What this component does

What this component does

WhenWhat happens
Once, at buildThe subclass's params are type-checked and its build_graph() runs, adding nodes to a DAG. Each node is a market-data or strategy-data leaf, a calculation taken from the registry by name, an inline Python expression, a named condition, or a named exit. A bad signal is refused before anything trades.
Before tradingIt says which calculations need history (daily, prior-session intraday, auxiliary), is seeded from that history, and reports whether every warmup calculation has a value.
Every barStrategy hands it the bar history and strategy data (entry price, seconds since entry). It steps every calculation and inline expression once, in dependency order.
When askedIt evaluates the entry logic and each named exit condition over this bar's values.
Entry decision → flatStrategyExecution freezes the inputs of the exit-side steps at the entry bar, and releases them when the trade is over.
Cold rebuildA fresh build from the same class, which Strategy then replays seed bars through.

It is pure: no I/O, no clock, and no knowledge of orders or position beyond what is passed in.

StrategySignal · Sample

Sample

This component has its own sample, separate from the system golden sample. The golden sample reaches it only as "entry true on the L-cross bar, exit true on the T bar", so it exercises neither warmup, rearm nor the exit-input freeze. This sample is a hand-made list of bars. Its signal class is written out in full under Skeleton code.

InputA signal class with:
  • one warmup calculation: sma5, a 5-bar simple moving average of the close, seeded from 5 prior bars;
  • entry logic: close > L, with rearm_required = True in its params, so entry fires only on the rising edge;
  • an exit-side step stop_px = sma5 − 2 ticks, which is an exit input;
  • exit condition stop: close < stop_px;
  • exit condition target: close ≥ T.
Five seed bars, then 10 synthetic bars. The close crosses L on bar 3 and keeps rising on bars 4–6, so sma5 rises. On bar 8 it falls below the bar-3 stop_px without reaching T. StrategyExecution freezes on bar 3; Strategy passes the entry price from bar 3 on.
ExpectedWarm after the seed; entry true on bar 3 only; stop_px holds its bar-3 value on bars 4–8; stop true on bar 8 only; target never true; exit_condition_level("stop") equals the bar-3 stop_px.
Passes whenOver bars 1–10 entry is true exactly once, on bar 3; exit is true exactly once, on bar 8, from stop; and stop_px read on bars 4–8 equals its bar-3 value.
Fails whenEntry is also true on bars 4–6 (the sustained run fired again, so the rising-edge gate is broken); or stop_px on bar 5 differs from bar 3 because it followed the live sma5 (the freeze is broken); or the signal reports warm before the seed.
StrategySignal · Behaviours

Behaviours

Each says what the signal is given, what it must do, and what must always stay true. Any implementation of the interface must meet all six.

1Build cold

Given
A SignalDag subclass and the slot's deployment config (for the signal instrument).
Must
  • Build the DAG by running build_graph(g, params): take every calculation from the registry by name and wire the inputs the graph passes it (market data, strategy data, other nodes). A node can only read nodes added before it, so the graph has no cycle.
  • Refuse a bad signal at build: a param value that does not match its type hint; an unregistered calculation name; a duplicate node name; no entry condition, or no exit; an unknown session; an unregistered market-data name, or one the session cannot supply; a non-bool rearm_required; a node named entry while rearm is on.
  • Resolve the params' session label (for example regular) to the instrument's session name from its exchange profile.
  • Tell each calculation that reads auxiliary history which market-data names its inputs read, so it picks its own series when an instrument carries more than one.
  • Start cold: no stepped values, no rising edge, no frozen inputs.
Invariant
A refused signal leaves no state behind for the next build, and two builds of the same class share nothing. Within one scope, a registry name is bound to exactly one class. A calculation name resolves in the signal's folder scope first, then in the built-in library.

2Step

Given
The bar history up to this bar, and strategy data.
Must
  • Step every calculation and inline expression once, in dependency order, so each step reads its inputs' values from this same bar. Warmup calculations stay at their seeded value.
  • Skip an inline step that cannot be evaluated yet (a missing input, or the entry price while flat); it is unavailable for this bar.
  • A step that fails on this bar is null for this bar. Its previous value is dropped, never carried, and it is remembered as stale, so level() and exit_condition_level() answer None for it.
Invariant
The values for a bar depend only on the signal class, the bars, the seed and the strategy data given so far.

3Evaluate entry/exit

Given
A stepped bar.
Must
  • Answer entry and exit from the signal's conditions over this bar's values.
  • Rearm. With rearm_required, entry is true only on the per-day rising edge of the entry logic. The edge is tracked on every bar, in position too.
  • Nulls. Logic is three-valued (Kleene): a null leg does not block an OR whose other leg is true, an AND with a false leg is false, and a result that is still null reads as false. With rearm on, a null entry is warned once per trading date, naming the missing refs. Any evaluation error other than a missing ref is raised.
  • Exit per condition. evaluate_exit_conditions() answers each exit condition by name, in the order the exits were added; the exit answer is their OR. Every condition is reported as evaluated — the signal knows nothing of resting broker exits.
  • Exit level. exit_condition_level(name) reports the level a condition of the shape close <op> step compares against: that step's value on the last stepped bar. It is None for any other shape, or while the value is unavailable.
  • Step level. level(name) reports any step's last value as a price; None for an unknown step, a value not computed yet, a step that failed on the last bar, or NaN. has_level(name) says whether the signal has that node. Reading any of these changes nothing.
  • Names and values. entry_conditions() answers each entry condition by name on the last stepped bar (None when it has no value). exit_condition_names() and condition_names() list names without evaluating, so they are correct before the first bar. values() returns a copy of every node's value on the last stepped bar (decision 8).
Invariant
With rearm on, a sustained run of true entry logic gives one entry, and the gate stays closed until the signal is warm. Evaluating has no side effect: asking twice on the same bar gives the same answers.

4Warm report and history needs

Given
History frames from Strategy (daily, prior-session intraday, auxiliary).
Must
Say which calculations need intraday, daily or auxiliary history, and how many months of daily bars. Seed the warmup calculations and report warm only when every one has a value. Let session-fixed calculations snapshot and restore their value; a restore also puts each restored value back, so the logic reads it before the next bar.
Invariant
A calculation whose history was empty or too short is never reported warm. A restored session-fixed value equals the one snapshotted.

5Exit-input freeze/release

Given
A freeze at the entry-decision bar, and later a release.
Must
After a freeze, exit-side steps read the calculation and market inputs captured at that bar, while the close, strategy data and every other step stay live. After a release they read live inputs again. Each freeze replaces the previous one. An exit-side step is one that reads strategy data, or one wrapped in g.freeze_at_entry() (decision 6).
Invariant
An input missing at the entry bar stays unavailable for the whole trade. A signal with no exit-side nodes is unaffected by freeze and release.

6Cold rebuild

Given
A rebuild request from Strategy (only ever while flat and idle).
Must
Build afresh from the same class, discarding every value, the rearm state and any freeze; Strategy then replays seed bars through it.
Invariant
After a rebuild and the same replay, the signal's values equal those of a fresh process given the same bars.
StrategySignal · How a signal is written

How a signal is written

A strategy author writes one SignalDag subclass in Python, in the strategy's folder under local/strategies/, and registers it by name with register_signal_dag. It has two parts:

PartWhat it holds
ParamsA frozen dataclass that extends SignalParams. Each field has a type hint and a default, and the defaults are the values: there is no params config (decision 9). SignalParams holds the fields every signal has: session, direction, max_trades_per_day, warm_up_months, rearm_required.
build_graph(g, p)Adds the nodes to the graph g, reading values from p.

The graph calls:

CallAdds
g.bar(field)A market-data leaf: a bar field, or a registered auxiliary name.
g.strategy_data(field)A strategy-data leaf (entry_price, secs_since_entry); null while flat. A node that reads it is exit-side.
g.calc(name, calc_key, *inputs, **params)A calculation from the registry, wired to its inputs.
g.expr(name, fn, *inputs)An inline pure Python function of its inputs; unavailable on a bar where an input is null.
g.warmup(node, history)Marks a calculation as seeded from daily, intraday or aux history and held at its seeded value.
g.freeze_at_entry(node)Marks a node as an exit input (decision 6).
g.condition(name, left, op, right)A named comparison.
g.any_of(name, *conditions)A named OR of conditions.
g.entry(*conditions)The entry logic: the AND of the conditions.
g.exit(name, left, op, right)A named exit condition. The exit answer is the OR of the exits, in the order they were added.

Every node has a name: level(), has_level(), the condition methods and values() use it. A variant with other values is a subclass that overrides Params. A new calculation is one class registered with register_calc in the strategy folder's calculations.py (System map R2). It is bound in that folder's scope, so another folder may use the same name; g.calc() looks a name up in the folder's scope first, then in the built-in library (System map decision 43). The SignalDag base class implements the whole interface, so a signal holds no stepping, evaluation, freeze, warmup or rebuild code. A different implementation can still plug in through the interface (decision 7).

"""StrategySignal interface (Alchemist v3, draft)."""

from __future__ import annotations

from abc import ABC, abstractmethod
from collections import deque
from dataclasses import dataclass
from typing import Any, Callable


@dataclass(frozen=True)
class WarmupRequirements:
    daily_months: int = 0                  # months of daily bars
    intraday: tuple[str, ...] = ()         # calculations seeded from prior-session bars
    daily: tuple[str, ...] = ()            # calculations seeded from daily history
    aux: tuple[str, ...] = ()              # calculations seeded from auxiliary series
    session_fixed: tuple[str, ...] = ()    # values safe to restore after a restart


class StrategySignal(ABC):

    @classmethod
    @abstractmethod
    def from_config(cls, strategy_config: dict) -> "StrategySignal":
        """Behaviours 1, 6: build cold from the slot config; refuse a bad signal."""

    @abstractmethod
    def warmup_requirements(self) -> WarmupRequirements: ...
    @abstractmethod
    def seed(self, history: dict) -> None: ...
    @abstractmethod
    def is_warm(self) -> bool: ...

    @abstractmethod
    def step(self, bars: deque, strategy_data: dict) -> None:
        """Behaviour 2 (and 3: drives the rearm gate every bar)."""

    @abstractmethod
    def evaluate_entry(self) -> bool: ...
    @abstractmethod
    def evaluate_exit_conditions(self) -> dict[str, bool]:
        """Behaviour 3: every named exit condition, in the order the exits were added."""

    def evaluate_exit(self) -> bool:
        return any(self.evaluate_exit_conditions().values())

    @property
    @abstractmethod
    def rearm_required(self) -> bool: ...
    @abstractmethod
    def exit_condition_level(self, name: str) -> float | None: ...
    @abstractmethod
    def level(self, name: str) -> float | None: ...
    @abstractmethod
    def has_level(self, name: str) -> bool: ...

    @abstractmethod
    def entry_conditions(self) -> dict[str, bool | None]:
        """Behaviour 3, decision 8: each entry condition's value on the last bar."""
    @abstractmethod
    def exit_condition_names(self) -> list[str]: ...
    @abstractmethod
    def condition_names(self) -> set[str]: ...
    @abstractmethod
    def values(self) -> dict[str, Any]:
        """Behaviour 3, decision 8: a copy of every node's value on the last bar."""

    @abstractmethod
    def freeze_exit_inputs(self, bar: dict) -> None: ...
    @abstractmethod
    def release_exit_inputs(self) -> None: ...

    def snapshot_session_state(self) -> dict: return {}
    def restore_session_state(self, state: dict) -> None: ...

@dataclass(frozen=True)
class SignalParams:
    session: str
    direction: str
    max_trades_per_day: int = 1
    warm_up_months: int = 0
    rearm_required: bool = False


class Graph:
    def bar(self, field: str) -> Node: ...
    def strategy_data(self, field: str) -> Node: ...
    def calc(self, name: str, calc_key: str, *inputs: Node, **params) -> Node: ...
    def expr(self, name: str, fn: Callable[..., Any], *inputs: Node) -> Node: ...
    def warmup(self, node: Node, history: str) -> Node: ...
    def freeze_at_entry(self, node: Node) -> Node: ...
    def condition(self, name: str, left: Node, op: str, right: Node | float) -> Node: ...
    def any_of(self, name: str, *conditions: Node) -> Node: ...
    def entry(self, *conditions: Node) -> None: ...
    def exit(self, name: str, left: Node, op: str, right: Node | float) -> None: ...


class SignalDag(StrategySignal):
    """The shipped implementation. A subclass gives only Params and build_graph()."""
    Params: type[SignalParams]

    def build_graph(self, g: Graph, p: SignalParams) -> None:
        raise NotImplementedError
    # Major state:
    #   params                  the type-checked Params instance
    #   _nodes                  nodes in the order build_graph() added them (a DAG order)
    #   _values                 node name -> value for the last stepped bar
    #   _rearm                  rising-edge gate: day, previous raw entry, armed
    #   _exit_inputs, _frozen   exit-side nodes; the entry-bar capture
    #   _stale                  nodes that failed on the last stepped bar


# alchemist/calculations/calculation.py
class Calculation(ABC):
    def setup(self, **params) -> None:
        """Behaviour 1: take params; start cold."""
    def step(self, *inputs) -> Any:
        """Behaviour 2: value for this bar; None = unavailable; raise = failed.
        Default: value()."""
    def warmup(self, data) -> None:
        """Behaviour 4: seed from history (default: nothing)."""
    def value(self) -> Any:
        """Behaviour 4: the seeded value, or None if not seeded."""
    def bind_aux(self, names: frozenset[str]) -> None:
        """Behaviour 1: optional, for calculations that read auxiliary history."""


class SessionFixedCalculation(Calculation):

The Sample's signal classpython · one SignalDag subclass 
# local/strategies/level_cross/strategy_signal.py
@register_signal_dag("level_cross")
class LevelCross(SignalDag):

    @dataclass(frozen=True)
    class Params(SignalParams):
        session: str = "regular"
        direction: str = "long"
        rearm_required: bool = True
        level: float = 100.0         # L
        target: float = 110.0        # T
        sma_period: int = 5
        stop_offset: float = 0.5     # 2 ticks of 0.25

    def build_graph(self, g: Graph, p: Params) -> None:
        close = g.bar("close")
        sma5 = g.warmup(g.calc("sma5", "sma", close, period=p.sma_period), history="intraday")
        stop_px = g.freeze_at_entry(
            g.expr("stop_px", lambda sma: sma - p.stop_offset, sma5))

        g.entry(g.condition("above_level", close, ">", p.level))
        g.exit("stop", close, "<", stop_px)
        g.exit("target", close, ">=", p.target)

StrategySignal · Decisions already made

Decisions already made

1Is the signal pure?

Yes: no I/O, no clock, no orders. Position data arrives only as strategy data (System map decision 21).

2Who decides when it steps, rebuilds, freezes?

Strategy steps and rebuilds it; StrategyExecution asks it questions and times the freeze (System map decisions 20, 22).

3Does the signal know about resting broker exits?

No. It reports every exit condition and each one's level; StrategyExecution decides which conditions a broker order already covers.

4Are the calculations part of StrategySignal?

Yes. The calculations are the DAG's nodes, so they and their tests belong to this component. They read session facts (first-bar anchor, which sessions count as regular trading hours) from the exchange profile, not from session names (System map decision 31).

Proposed · not agreed

5How is a signal written inside the boundary?

As a Python SignalDag subclass registered by name: typed params it holds itself, and a build_graph() that adds registered calculations, inline Python expressions, named conditions and named exits to the DAG. The SignalDag base class implements the whole interface. The instrument comes from deployment config and the session from the exchange profile.

Rejected: a declarative definition file (a second format to parse and check; a Python class is checked at import and build); class-attribute nodes built with operator overloading (an exit level must stay readable as close <op> node, and every node needs a name); interface only, with no signal shipped (every user would have to bring a signal layer).

proposed · v3 · changed 2026-11-07 · closes the System map open question

6How is a node marked as an exit input?

A node that reads strategy data is an exit input. A signal may also wrap any node in g.freeze_at_entry(), so a stop built from live calculations alone (like the Sample's stop_px) can be frozen at entry without reading the entry price.

Rejected: strategy-data nodes only (a stop that does not read the entry price could not be frozen).

proposed · v3 · to confirm

7Why put an interface in front of one implementation?

So Strategy and StrategyExecution can be tested against a small fake signal, and so a different signal layer can plug in without engine changes (System map R2). SignalDag is still the only one the engine ships.

proposed · v3

8What may a caller read from the signal?

Only its public interface. For logs and startup checks the interface has read-only methods: entry_conditions(), exit_condition_names(), condition_names() and values(). A restore after a restart goes through restore_session_state(), which also puts the restored values back. No caller reads a signal's private state.

Rejected: callers reading the signal's value cache or its logic structure directly (they would depend on one implementation's private layout, so another implementation could not plug in).

proposed · v3 · 2026-11-07

9Where do a signal's params live?

In its Params dataclass; the defaults are the values. The build type-checks every field against its type hint. A variant with other values is a subclass that overrides Params. Version control of a strategy's code and params is outside the system.

Rejected: params in outside config (a second place that must agree with the code).
