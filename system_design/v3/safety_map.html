Safety

The watchdog. It keeps checking that the broker connection and the price feed are alive, climbs a ladder of fixes when they are not, and afterwards repairs any strategy left waiting on an order whose outcome it missed.

v3 draft, 2026-11-06 — not agreed. Behaviours 1–9 and decisions 1–4 are settled. Behaviour 10 is proposed. Multi-asset: the feed watchdog arms on every configured exchange's data session.

Safety · Goal

Goal

Keep watching the broker socket and the market-data feed; run escalating recovery steps and exponential-backoff reconnects when they fail; and repair strategies stranded during a disconnection by attributing and re-creating the fills they missed, from the broker's executions.

Owns, from the System map:

Detecting a lost broker connection or a frozen process, reconnecting, and un-sticking any strategy left waiting on an order whose fill happened during the outage.

Safety · What this component does

What this component does

Safety runs its own asynchronous heartbeat loop with two layers of checks:

LayerChecksHow often
Layer 0 — socketThe Gateway socket answers.Every 5 seconds.
Layer 1 — feedMarket data is fresh: a tick within 45 s.While an exchange's data session is open.

When a check fails it climbs a recovery ladder, cheapest step first:

  1. resubscribe in place, with backoff;
  2. full socket reconnect, with exponential backoff that never stops;
  3. restart the broker gateway process — only inside the maintenance window.

After reconnecting it re-establishes the Gateway subscriptions and runs repair: it asks the broker for executions and open orders by order id, and puts any missing Filled or Rejected order update into the Event Loop's buffer, freeing any strategy parked waiting on an order.

Sample

The system golden sample from the System map, combined with a component-level outage test.

Golden sample (clean run)Outage injection
InputClean feed, no socket disconnect. Safety watches and does nothing.The broker socket drops for 10 seconds while a strategy is in PROCESSING_ENTRY_ORDER with order id 42; the broker executes the order at 5000.0; the socket reconnects.
ExpectedExactly zero reconnect attempts, zero repairs, clean monitoring.Detects the socket failure within 5 s; starts reconnecting; asks for broker executions on reconnect; finds order 42 filled at 5000.0; puts a Filled order update (order 42, average price 5000.0) into the event buffer; the parked strategy moves to IN_POSITION_ACTIVITY.

Passes when the socket drop triggers an exponential-backoff reconnect without crashing; repair fetches executions, matches order 42 and enqueues a re-created fill event; and clean runs produce no duplicate fills or false repairs.

Fails when a cut connection is not noticed within the heartbeat thresholds; the reconnect loop stops retrying after repeated failures; a stranded strategy stays frozen waiting on an order for good; or a fill is attributed to the wrong strategy.

Safety · Behaviours

Behaviours

1Socket heartbeat (Layer 0)

Given
A watchdog timer firing every 5 seconds.
Must
Call gateway.heartbeat(); if the probe fails, start the socket-dead reconnect loop at once.
Invariant
A socket failure is caught within one heartbeat interval plus the timeout; the failure counter only goes up until the connection is restored.

2Feed liveness (Layer 1)

Given
An active session where ticks are expected.
Must
Check that now − gateway.last_tick_ts is under 45 s; if not, start the escalating feed-recovery ladder.
Invariant
Staleness is checked only while the continuous data session of at least one configured exchange is open, from its exchange profile — for CME, Sunday 18:00 → Friday 17:00 New York less the daily break and early closes; for Eurex, its own trading hours on the Frankfurt clock — so a day-session-only book is still watched overnight, and there are no false alarms when every configured exchange is in its break or weekend. The Gateway's last-tick time likewise counts only instruments whose exchange is open (Gateway behaviour 2).

3Escalating recovery ladder

Given
The tick feed stays silent during an active session.
Must
Climb the rungs in order:
  1. resubscribe with exponential backoff (up to 4 attempts);
  2. full socket reconnect;
  3. broker gateway process restart (only inside the nightly maintenance window).
Invariant
Cheaper in-process rungs always come before any external process action; a process restart is strictly limited to the configured maintenance windows.

4Reconnect that never gives up

Given
A confirmed socket disconnection.
Must
Run a continuous reconnect loop with exponential backoff, delay(n) = min(cap, base · 2^(n−1)), logging CRITICAL on persistent failure without aborting.
Invariant
The loop never gives up or ends until the connection is re-established.

5Restore subscriptions after reconnect

Given
A successful socket reconnect.
Must
Call the reconnect callbacks to restore streaming ticks for every instrument, order execution updates and account subscriptions.
Invariant
Every Gateway data and order feed the engine needs is confirmed restored before normal monitoring resumes.

6Order attribution and repair

Given
After a reconnect, the strategies with submitted, open or cancelling orders (asked through Strategy — Order Manager's answer). This is not gated on the execution phase, so a resting stop that filled while the slot held a position is repaired too. Each order is repaired on its own. The steady-state audit (Event Loop behaviour 6) calls the same repair but hands it only the strategies whose is_processing_order() is true.
Must
Match pending order ids against broker executions from gateway.get_executions(); on a match, create a Filled order update and append it to the event buffer.
Invariant
Attribution is strictly by unique order id. Fills are never inferred from net position, so assignment stays correct when several strategies trade the same instrument.

7Dead orders become Rejected

Given
A pending order older than 120 s that is confirmed absent from both the broker's executions and its open orders.
Must
Put a terminal Rejected order update into the event buffer to free the waiting strategy.
Invariant
An order is declared dead only when it is confirmed absent from both the executed and open sets after the minimum-age grace window.

8Frozen-loop detection

Given
The event loop blocked past the freeze threshold.
Must
Dump every thread's stack once the loop has missed its check-ins for the threshold; a healthy check-in resets the counter.
Invariant
A healthy loop never triggers a dump.

9Positions polloff by default

Given
Positions polling enabled in config.
Must
On the heartbeat loop, at most once per poll interval, fetch broker positions and enqueue them as position updates. A failing fetch is logged, swallowed and throttled.
Invariant
When disabled, the heartbeat loop never polls. The poll never changes any strategy's position (monitoring only).

10Membership read from the runtime bookproposed · System map decision 34

Given
A strategy committed to the Event Loop's runtime book after Safety was built.
Must
Safety holds the book, not a copy of the strategy list: repair, periodic reconciliation, the positions poll and the data watchdog read the book's strategies when they run. A reconnect resubscribes the book's fed instruments, once per instrument.

Safety · Decisions already made

Decisions already made

1Why two layers of watching?

Layer 0 watches socket responsiveness; Layer 1 watches tick-feed freshness — because the socket can stay alive while the feed is dead.

2How are repaired fills attributed?

Strictly by order id, never by net position, so attribution stays correct even when several strategies trade the same instrument.

3How is a resubscribe livelock avoided?

The broker's "connectivity restored" signals (at IBKR, 1101/1102) are capped at 3 consecutive resubscribes without a tick, then Safety falls through to a socket reconnect.

4When is a missing order safely declared dead?

Only when it is older than 120 seconds and confirmed absent from both the execution history and the open-order snapshot — preventing races with orders still in flight.
