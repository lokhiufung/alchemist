Gateway

The engine's only line to the broker. Prices come in through it, orders go out through it, and fills come back through it. In simulation, a simulated broker sits behind the same interface.

v3 draft, 2026-11-07 — not agreed. Behaviours 1–9 and decisions 1–6 are settled. Behaviours 10–15 and decision 7 are proposed. Multi-asset: contract identity, venue and session clocks come from each instrument's exchange profile (behaviour 13).

Change history
  • 2026-11-07 — New behaviour 15 and decision 7: the simulated broker prepares all replay data itself, on request; the runner writes no data files (System map decision 45).
Gateway · Goal

Goal

Give the rest of the engine one uniform, asynchronous interface to the execution broker (or the simulated broker). Through it the engine reliably receives streaming market ticks for every instrument it trades, sends orders, tracks executions, and sees whether the connection is healthy.

Owns, from the System map:

All communication with the broker: market data in, orders and cancels out, fills and executions back, for every instrument the process trades. A replay source can stand in for the broker behind it.

Gateway · What this component does

What this component does

The Gateway sits on the boundary between the outside world (the broker's API, or a replay data source) and the engine.

DirectionWhat happens
ConnectionConnects to the broker API or the replay source.
ContractsDerives each instrument's tradable contract on its venue, from its exchange profile and asset class (a future's current contract by roll rule; a stock's one listing; options open, see System map open questions): CME in USD for NQ and ES, Eurex in EUR for FDAX. Where the broker lists several products under one symbol (FDAX, FDXM and FDXS all appear as DAX at IBKR), the instrument's trading class tells them apart.
In: pricesTakes raw market ticks and pushes them onto the central event buffer.
Out: ordersReceives orders and sends them to the broker. In simulation, its internal fill engine fills them instead.
In: updatesPuts order status, position and balance updates on the buffer.
QueriesAnswers questions about executions, open orders and positions.
HealthExposes a socket heartbeat, feed liveness and reconnect hooks to Safety.
Gateway · Sample

Sample

The Gateway's slice of the system golden sample from the System map.

InputA synthetic session of 1-second price ticks for one instrument that rises through level L and later reaches target T, entering through the Gateway in replay mode. Two market orders are sent one after the other: BUY 1 MKT when L is crossed, SELL 1 MKT when T is reached. Then end of data.
ExpectedEvery tick lands in the event buffer in time order, followed by end_of_data. Each order is accepted, gets a unique order_id, and produces a matching FILLED order update. get_executions() returns exactly two execution records, each tagged with the order_id it came from.
Passes whenAll synthetic ticks appear in the buffer with time never going backwards; exactly two orders produce two filled order updates; get_executions() returns two rows matching the orders' IDs; and heartbeat() returns True.
Fails whenAny tick is dropped, duplicated or out of order; an order does not produce an order update; an execution row is missing its originating order_id; or heartbeat() fails to notice a disconnected socket.
Gateway · Behaviours

Behaviours

Each behaviour says what the Gateway is given, what it must do, and what must always stay true.

1Connection lifecycle

Given
The Gateway's configuration, or a reconnect request from outside.
Must
Connect to, disconnect from, or reconnect to the broker or replay source, and update the connection status.
Invariant
A successful connect or reconnect brings back the order-status, account and market-data streams the engine needs, for every instrument.

2Market data streaming

Given
An active contract subscription and incoming price ticks from the broker or replay source.
Must
Append each tick event to the event buffer in time order and update the last-tick time. Once each instrument's session is declared, the last-tick time counts only instruments whose exchange's data session is open, so a closed Eurex feed does not look dead while CME trades on.
Invariant
Tick events keep their price, size, instrument and non-decreasing timestamps.

3Placing orders

Given
A valid order from Order Manager: instrument, action, size and order type (MKT, STP or LMT), with a stop price for STP and a limit price for LMT, and optionally an OCA group and OCA type on any type.
Must
Give the order a unique order_id, send it to the broker or the simulated broker, and put the resulting order update on the event buffer. Also:
  • Tick rounding. For STP and LMT, round the price to the contract's minimum tick — BUY STP and SELL LMT round up, SELL STP and BUY LMT round down — and write the rounded price back into the order. At IBKR, stops trigger on last price.
  • Local rejects. A priced order without a valid price (missing, zero, negative, NaN or not a number) or without a known minimum tick is rejected before anything is sent. An order with an OCA group must carry OCA type 1, 2 or 3 — there is no default, the caller chooses — or it is rejected locally.
  • Time in force. Every order is DAY and allowed outside regular hours.
  • Contract identity. Resolved contracts, tick subscriptions, minimum ticks, fills and positions are all keyed by the engine's instrument, so FDAX and FDXS never collide on the broker's shared DAX symbol.
  • Simulation. The simulated broker rests STP/LMT orders (emitting OPEN) and matches them on each later bar of the instrument: a touch fills at the level, a gap fills at the open, the stop wins when both legs of a group fire, and the group's other legs become CANCELLED. An order into an already-filled OCA group is REJECTED; a MKT into a working group cancels the legs first. A resting fill is booked after strategies have seen its bar — one bar later than live, accepted.
Invariant
Every placed order gets a distinct, increasing order_id and eventually ends FILLED, CANCELLED or REJECTED. An STP/LMT price sent to the broker is always on tick.

4Cancelling orders

Given
An active order_id still pending at the broker.
Must
Send a cancel request to the broker and put a CANCELLED order update on the buffer once it is confirmed.
  • When the broker refuses the cancel (at IBKR, errors 10147, 10148, 161), put a CANCEL_REJECTED order update for that order id. Never forward the broker's intermediate pending-cancel status.
  • The simulated broker cancels only a resting order (→ CANCELLED); any other id gets no event.
Invariant
A cancelled order never produces another fill. A refused cancel never produces a CANCELLED.

5Broker state and execution queries

Given
A request for broker executions or open orders, optionally filtered by a since-timestamp.
Must
Fetch the broker-side execution rows and open-order snapshots.
Invariant
Every execution record includes order_id, instrument, side, fill quantity, average price, currency, fill time and execution id, so each fill can be traced to its order without doubt.

6Socket heartbeat

Given
A heartbeat probe from Safety.
Must
Query the broker endpoint (for example its current-time request) and return True if it answers within the timeout, False otherwise.
Invariant
Returns True if and only if the socket answers within the latency threshold.

7History and intraday seed

Given
An instrument, a history window and a session.
Must
Fetch historical bars for warmup and intraday seeding before the session trades.
  • Daily frame. Built from intraday bars over the full session, clipped and aggregated per trading date, with bar dates normalised to UTC. The window ends at the last completed session's real close, on that session's own clock.
  • Contract roll. Before a roll is complete, history that depends on liquidity is taken from the previous contract, and the Gateway can name the sessions where the feed is the new, still-thin contract.
  • Replay. The simulated broker builds its daily frame from the replay tape, with the same definitions, when the Event Loop asks for it (behaviour 15).
Invariant
History arrives in time order, with no look-ahead past the requested window. A value the frame cannot serve exactly is never served silently.

8Account, position and balance updates

Given
Account subscriptions, or a request for a position snapshot.
Must
Put position updates (signed size, side, average price, account; flat for zero) and balance updates (available funds per account and per currency) on the buffer, from the broker's streams or, in simulation, from the simulated book. Answer position snapshots for the configured accounts. Broker decimals become floats.
Invariant
Every update carries its account, and every money amount its currency. A snapshot that times out raises an error and leaves no waiter behind.

9Broker status messages

Given
Error and status messages from the broker.
Must
  • Ignore harmless codes.
  • Track connectivity and each data farm's status; on recovery, raise a one-shot resubscribe request.
  • Turn an order reject into a Rejected order update by order id — never for a data request id. At IBKR the order-reject codes are 110, 200, 201, 203, 321, 401 and 512. Code 401 (an order field failed validation) gets no order status from the broker, so without this the order would sit pending, unprotected, until Safety's repair declared it dead.
  • Resolve or fail pending history requests according to their codes.
Invariant
No status message ever stops the engine or invents an order update.

Proposed · not agreed

10An explicit interfaceproposed · System map decision 30

Given
A new concrete gateway.
Must
  • Implement every required method (connect, disconnect, reconnect, orders, cancels, contracts, subscriptions, history, executions, positions); building a gateway that misses one fails at once.
  • Override a gateway capability only when it has one; the interface's default is safe. Capabilities: feed liveness, the resubscribe request, market-data readiness, roll-mismatch dates, commissions, the current bar for simulated fills, session declaration, and whether a failed intraday seed is fatal.
  • Register under a name; the runner picks the gateway by that name.
Invariant
No caller looks a gateway method up by name.

11History in broker-neutral unitsproposed · System map decision 30

Given
A history request from the Event Loop.
Must
Take the window as months (or start/end dates) and the session; each gateway turns it into its own broker's request. Broker-specific duration strings are built inside that gateway only.
Invariant
Behaviour 7's invariant holds: history in time order, no look-ahead.

12Wake the Event Loopproposed · System map decision 26

Given
The gateway has appended an event to the event buffer from any thread.
Must
Raise the Event Loop's drain wake-up through a thread-safe call into the loop.
Invariant
The reader thread never touches loop state except through the loop.

13Exchange facts from the exchange profileproposed · System map decisions 31, 37

Given
An instrument to qualify, subscribe or fetch history for.
Must
Read its contract venue, currency, broker contract identity, roll rule and session clocks from its exchange profile; no exchange special case in gateway code.
Invariant
A new exchange needs a new exchange profile, not gateway edits (unless the broker itself differs).

14Serve a strategy added while runningproposed · System map decisions 34–36

Given
The Event Loop staging a candidate strategy in a running paper/live process.
Must
  • Resolve a contract and subscribe ticks for an instrument new to the process, while the existing feeds keep running.
  • unsubscribe_tick(contract): release a tick subscription when a failed candidate's new instrument is cleaned up. A no-op where feeds cost nothing (the simulated broker).
  • Re-declare instrument sessions from the runtime book when a new instrument is reserved, so a new Eurex feed is judged on the Frankfurt clock, not the CME one.
  • Answer the candidate's admission check from the existing positions and open-orders reads; a broker that does not answer makes the request unmanaged_exposure.
Invariant
Adding a strategy never re-subscribes or drops a feed a running strategy uses.

15The simulated broker prepares its own dataproposed · System map decision 45

Given
Replay settings from the config: a tape source, a replay date and a session.
Must
  • Read the tape lazily, and collect only the rows each request needs.
  • Check, before replay starts, that every row in the replay window and the history it serves falls inside the session, using the exchange profile's session hours, calendar and early closes. One generic check serves every exchange. Refuse a tape with rows outside the session, and a day-session-only tape given for an overnight session.
  • Answer get_daily_history and get_intraday_seed_bars from the tape when asked, like the broker gateway. Return an empty list when the tape has no prior session.
  • Pad the replay window before and after the session with flat bars, as a simulated broker option.
  • A synthetic generator is a second tape source behind the same simulated broker.
Invariant
The runner writes no data files and reads no strategy before the strategy exists. Replay history has the same definitions as broker history (behaviour 7).

"""Skeleton contract for the Gateway component (Alchemist v3, draft)."""

from __future__ import annotations

from abc import ABC, abstractmethod
from collections import deque
from datetime import date
from typing import Any

from alchemist.instruments import Instrument


class Gateway(ABC):
    """Base of every broker gateway and of the simulated broker."""

    event_buffer: deque
    #   the one shared queue the Event Loop drains; entries are
    #   {'event_type', 'data', 'enqueued_at'} with event_type in
    #   tick, order_update, position_update, balance_update, end_of_data

    # ---- required (Behaviours 1-9) ----
    @abstractmethod
    async def connect(self) -> None:
        """Behaviour 1: connect to the broker or replay source."""

    @abstractmethod
    async def disconnect(self) -> None:
        """Behaviour 1: close the connection and release resources."""

    @abstractmethod
    async def reconnect(self) -> None:
        """Behaviour 1: re-establish the connection and restore subscriptions."""

    @abstractmethod
    async def subscribe_order_update(self) -> None:
        """Behaviour 1: subscribe to order status updates."""

    @abstractmethod
    async def resolve_contract(self, instrument: Instrument) -> Any:
        """Behaviour 3: qualify the instrument's current contract (exchange profile roll rule)."""

    @abstractmethod
    async def subscribe_tick(self, contract: Any) -> None:
        """Behaviour 2: subscribe to real-time ticks."""

    @abstractmethod
    def next_order_id(self) -> int:
        """Behaviour 3: a monotonic, unique order id."""

    @abstractmethod
    async def place_order(self, order: dict[str, Any]) -> None:
        """Behaviour 3: round, validate, send; queue the order update."""

    @abstractmethod
    async def cancel_order(self, order_id: int) -> None:
        """Behaviour 4: cancel a pending order."""

    @abstractmethod
    async def get_executions(self, since: float | None = None) -> list[dict[str, Any]]:
        """Behaviour 5: execution rows, each with its order_id and currency."""

    @abstractmethod
    async def get_open_orders(self, timeout: float = 5.0) -> list[dict[str, Any]]:
        """Behaviour 5: orders still working at the broker."""

    @abstractmethod
    async def heartbeat(self, timeout: float = 3.0) -> bool:
        """Behaviour 6: True iff the socket answers within the timeout."""

    @abstractmethod
    async def get_daily_history(self, instrument: Instrument, start: date,
                                end: date, session: str) -> Any:
        """Behaviours 7, 11: daily frame in broker-neutral units, no look-ahead."""

    @abstractmethod
    async def get_intraday_seed_bars(self, instrument: Instrument, session: str) -> list:
        """Behaviour 7: prior-session 1-second bars for intraday seeding."""

    @abstractmethod
    async def subscribe_account_update(self) -> None:
        """Behaviour 8: account, position and balance streams."""

    @abstractmethod
    async def get_positions(self, timeout: float = 5.0) -> list[dict]:
        """Behaviour 8: position snapshot for the configured accounts."""

    # ---- capabilities with safe defaults (Behaviour 10) ----
    @property
    def last_tick_ts(self) -> float | None:
        """Behaviour 2: last tick on an instrument whose data session is open."""
        return None

    def set_instrument_sessions(self, sessions: dict[Instrument, str]) -> None:
        """Behaviours 2, 14: which data session judges each instrument's feed."""

    def market_data_ready(self) -> bool:
        return True

    def consume_resubscribe_request(self) -> bool:
        """Behaviour 9: read and reset the one-shot resubscribe request."""
        return False

    def roll_mismatch_dates(self) -> frozenset:
        """Behaviour 7: sessions served by a newly rolled, still-thin contract."""
        return frozenset()

    async def get_commissions(self) -> dict[str, dict]:
        return {}

    def on_bar(self, instrument: Instrument, bar: dict[str, Any]) -> None:
        """Behaviour 3: current bar from the Event Loop; drives simulated fills."""

    def intraday_seed_failure_is_fatal(self) -> bool:
        return False

    async def unsubscribe_tick(self, contract: Any) -> None:
        """Behaviour 14: release a failed hot-add candidate's new feed."""

Gateway · Decisions already made

Decisions already made

1One Gateway interface for live and simulation?

Yes — one Gateway interface covers both the live broker and simulation/replay.

Rejected: splitting it into separate market-feed and order-router components.

2Where does simulated execution live?

Inside the simulated broker, which holds a fill engine (bar reference price, optional slippage in ticks) and presents exactly the same asynchronous interface and events as the broker gateway.

3How are executions attributed?

Every execution row carries its order_id, so Safety's repair can attribute fills correctly even when several strategies trade the same instrument at once.

4How is data liveness tracked?

The last-tick time is a property on the Gateway, so Safety can watch feed liveness separately from the socket heartbeat.

5Who rounds resting prices?

The Gateway, silently, choosing the direction from side and type, with one shared rounding helper the simulated broker also uses.

6What about the broker's pending-cancel status and refused cancels?

Pending-cancel is dropped: Order Manager learns of a cancel only from the final Cancelled. A refused cancel becomes a CANCEL_REJECTED update by order id.

Proposed · not agreed

7Who prepares replay data?

The simulated broker (SimulationGateway), on request, from a tape source (behaviour 15). The runner only names the tape, the date and the session in config.

Rejected: the runner slicing the tape and writing history files before start (a second history path beside the Gateway, and it must read strategies before they exist to know which columns to build).
