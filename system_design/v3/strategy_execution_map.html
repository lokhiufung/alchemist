StrategyExecution · 1 · Goal and scope

Goal and scope

What it is. StrategyExecution is the decision state machine inside each slot. StrategyExecution knows which phase the slot is in, asks the signal only the question that phase needs, sends only the orders that phase allows, and decides what each order event means. Three classes share one contract: the base class (bar-close market entries and exits), ProtectedStrategyExecution (resting broker-side exits in an OCA group) and StopLossProtectedStrategyExecution (one resting disaster stop). The slot's execution block in the config picks the class.

Why it exists. Resting broker-side exits make the order flow the hard part of a strategy: a stop can fill while the engine sends a market exit, a leg can be rejected, an exit can fail in position. Keeping that state machine apart from the signal (pure logic) and from Order Manager (order bookkeeping) lets each part be reasoned about and tested alone (System map decision 14).

Goal. Each slot moves through its execution phases correctly and sends only the entry and exit orders those phases allow. A protected slot never sends a market exit outside the trade's OCA group while a protective order may still fill, and never leaves an open position without protection that the slot has not accounted for.

Feature cards

1One trade at a time, up to the daily capsettled · both classes · was behaviour 1

Need
A slot must never have two orders in flight, never trade past its daily cap, and must keep its exit levels fixed at the entry bar for the whole trade.
Upstream gives
Bars from Strategy, the signal's entry and exit answers (StrategySignal feature 3), and order outcomes from Order Manager (Order Manager feature 4).
Algorithm
  1. On every in-session bar, in every phase (including DONE, ERROR and SESSION_END_FLATTENING), call the step-signal callback exactly once, before the phase logic. The signal then holds that bar's values, and the rearm gate sees every bar.
  2. While flat, ask for the entry answer on each in-session bar; on true, freeze the signal's exit inputs, then send one entry order.
  3. On the entry fill, be in position. On a bar-close exit answer, send one exit order.
  4. On the exit fill, be flat, count the round trip, release the frozen inputs, and go to DONE at the daily cap.
  5. A dead entry returns to entry seeking and releases the inputs; a dead exit returns to in position.
Parameters
ParameterConfigurable?SupportedDefault
Daily cap (round trips per day)Configurable per signal (max_trades_per_day)any positive count1
Quantity per entryFixed by System map decision 241 unit1 unit
Invariant
For every cap: at most one order in flight; no order after the cap; a trade's frozen inputs are never released while the trade is open.

2One question answers "processing an order?"settled · both classes · was behaviour 2

Need
Safety's repair, the Event Loop's stuck-order check and shutdown must know whether a slot waits on an order's outcome, without reading phase names.
Upstream gives
The current phase, and Order Manager's submitted, open and cancelling orders.
Algorithm
  1. Answer true in PROCESSING_ENTRY_ORDER and PROCESSING_EXIT_ORDER, and for a protected slot in PROCESSING_PROTECTION_ORDERS.
  2. In SESSION_END_FLATTENING, answer true only while an order of the slot may still fill.
  3. Answer false in every other phase, including IN_POSITION_PROTECTED.
Parameters
None.
Invariant
The only phase questions asked from outside are this one and "quarantined?" (feature 10). No caller reads phase names. Questions about orders are answered by Order Manager.

3Protect on entrysettled · protected · was behaviour 3 · decisions 14, 22

Need
A protected slot needs broker-side exits that fill even when the engine is down, sized to what actually filled and placed at levels computed from the actual fill price.
Upstream gives
The entry order closed with its filled quantity and average price (Order Manager), and the selected conditions' levels from the signal (exit_condition_level, or level(name) for the stop-loss class).
Algorithm
  1. On the first bar in position after the entry closed with filled quantity > 0, once per trade: take the selected levels for the actual average fill price. Placement is bar-driven, because the level needs the fill price and the order-update handler cannot await a group placement.
  2. If no level is available, or the latest close already crossed the stop, run this trade unprotected (stay in IN_POSITION_ACTIVITY).
  3. Otherwise request one group of the selected legs, sized to the filled quantity, under a fresh OCA group; enter PROCESSING_PROTECTION_ORDERS; when every leg is OPEN, enter IN_POSITION_PROTECTED.
  4. Stop-loss class: the level is the signal's node level moved by the offset against the trade (long: below, short: above); one STP leg.
Parameters
ParameterConfigurable?SupportedDefault
Resting exitsConfigurable per slot (execution block)map of exit-condition names to STP or LMT, at most one of each— (required)
Stop-loss level nameConfigurable per slot (stop-loss class)any node of the signal— (required)
Stop-loss offset (points)Configurable per slot (stop-loss class)any number of points— (required)
Invariant
Protection is sized to the confirmed filled quantity; at most one group per trade; no group for a zero fill or a crossed stop.

4Mask a condition only while a leg covers itsettled · protected only · was behaviour 4 · decisions 10, 15

Need
A selected condition that a resting leg covers must not also trigger a market exit, but no selected condition may ever go unwatched.
Upstream gives
The signal's per-condition exit answers on each bar in position (StrategySignal feature 3).
Algorithm
  1. In IN_POSITION_PROTECTED: send a bar-close market exit only when a non-selected condition is true and no selected condition is true. When a selected condition is true, send no market exit that bar, even if a non-selected condition is also true, and log the skip.
  2. In PROCESSING_PROTECTION_ORDERS and IN_POSITION_ACTIVITY: judge every condition at bar close.
  3. Log every raw condition answer.
  4. Stop-loss class: mask nothing; judge every condition at bar close in every phase.
Parameters
None.
Invariant
On every bar of an open position, each selected condition is covered by a working leg or by bar-close evaluation.

5A market exit joins the groupsettled · protected · was behaviour 5

Need
A market exit sent while a protective leg may still fill could fill twice. A cancel before the market exit would leave the position unprotected for a moment.
Upstream gives
The trade's group and its legs' states (Order Manager). The broker fills a market order in the OCA group and cancels the legs, or refuses it when a leg already filled (at IBKR: Inactive + error 201, normalised to REJECTED by the Gateway).
Algorithm
  1. While at least one leg is submitted or open: send one market order sized to the trade's position, carrying the group's OCA group and OCA type, with no cancel before it; enter PROCESSING_EXIT_ORDER.
  2. With every leg dead: send a plain market order.
  3. On the fill, complete the round trip. On a reject or cancel: if flat, a leg fill already closed the trade (feature 6); otherwise return to IN_POSITION_PROTECTED when every leg is still OPEN, else IN_POSITION_ACTIVITY, and the exit counts as failed (feature 12).
Parameters
ParameterConfigurable?SupportedDefault
OCA type of a joined exitFixed (same as the group, Order Manager feature 2)22
Invariant
No market exit outside the group while a leg may still fill; no cancel before a market exit; a market exit never exceeds the trade's position from Order Manager's filled quantities.

6A resting fill completes the tradesettled · protected · was behaviour 6

Need
A leg can fill in any phase, before its acknowledgement or while a market exit is in flight. Every fill that makes the slot flat must count exactly one round trip.
Upstream gives
Order updates through Strategy, and each order's filled quantity from Order Manager.
Algorithm
  1. Interpret each update by the order it is for (entry, exit, or a leg of the trade's group), not by the current phase.
  2. When the position is flat, complete the round trip exactly like a bar-close exit (count, release the frozen inputs, daily cap → DONE), with no market order.
  3. A later update for an order of a closed trade (the sibling's Cancelled, a refused market exit) changes no phase.
Parameters
None.
Invariant
Every fill that makes the slot flat completes exactly one round trip.

7Lost protection falls back to bar-close exitssettled · protected · was behaviour 7 · decision 18

Need
When a leg is rejected or cancelled while the position is open, the slot must still watch every exit condition, without placing a second group.
Upstream gives
A leg's Rejected or Cancelled update that was not caused by the trade's own market exit or a sibling fill.
Algorithm
  1. Enter IN_POSITION_ACTIVITY and judge every condition at bar close from then on; do not place the leg again.
  2. Later market exits still join the group while a leg survives, and go out plain once no leg survives.
  3. Log CRITICAL. Leave the surviving leg working.
Parameters
None.
Invariant
At most one group per trade.

8Trade only while warm and in session; reset each daysettled · both classes · was behaviour 8

Need
A slot must not enter before the signal is warm or outside its session, and must get its daily quota back on each new trading date.
Upstream gives
Warmup-ready and aux-ready from Strategy (Strategy feature 3), and the instrument's exchange profile with sessions, holidays and the overnight session roll.
Algorithm
  1. Seek entries only while ready_to_arm (warmup-ready AND aux-ready) holds and the bar is in session. Strategy is the only writer of both flags (System map decision 52). A half-session holiday counts as closed; if the calendar is unavailable, fall back to open.
  2. On the first bar of a new trading date (overnight sessions: at the session roll, not midnight), reset the round-trip count and let a DONE slot trade again, without disturbing an open position.
Parameters
None.
Invariant
No entry order while not warm or out of session.

9The round-trip count survives a restartsettled · both classes · was behaviour 9

Need
A process restart mid-day must not give the slot a fresh daily quota.
Upstream gives
A round-trip store, which can be missing or hold no record for today.
Algorithm
  1. Persist the count on each completed round trip and on the daily reset.
  2. On restart in session, restore the same-day count and park in DONE when the count is at or over the cap.
  3. With no store, no record, or outside session, start from zero.
Parameters
None.
Invariant
A restart never lets the slot exceed its daily cap.

10A quarantined slot sends nothingsettled · both classes · was behaviour 10

Need
The Event Loop quarantines a slot that keeps raising (Event Loop feature 6). The slot must stay silent until release, and release must not reset the daily quota.
Upstream gives
Quarantine and release calls through Strategy.
Algorithm
  1. Stay in ERROR and place no order on every bar.
  2. Log a reminder at most once per reminder interval per quarantine, with how long the slot has been parked.
  3. On release, restart from WAITING_FOR_WORKING_HOURS, except a slot quarantined while DONE, which returns to DONE on the same trading date.
Parameters
ParameterConfigurable?SupportedDefault
Reminder intervalConfigurable per process (System map decision 58)any positive seconds300 s
Invariant
An ERROR slot never sends an order; a quarantine and release never lets the slot exceed its daily cap.

11Session-end flattensettled · both classes · was behaviour 11

Need
At a session's cutoff, at shutdown, or after a failed exit, the slot must end flat with no market order sent next to an order that may still fill.
Upstream gives
A flatten request with the booked position from Strategy (Strategy feature 4), on each call until done.
Algorithm
  1. Enter SESSION_END_FLATTENING. On each call: cancel every open order; while Order Manager has a submitted, open or cancelling order, wait; when flat, go to DONE; otherwise send one market order for the booked position, with no OCA group.
  2. Do not resend a rejected flatten order on the same trading date, even across a quarantine.
  3. While flattening, step the signal (feature 1) but take no other action on a bar, and let no order update change the phase; the flatten fill counts no round trip.
Parameters
None.
Invariant
No market order while an order of the slot may still fill; at most one flatten market order per trading date; the same rule for every class.

12A failed exit is never resentsettled · both classes · was behaviour 12

Need
An exit that the broker rejected or cancelled in position must not be retried blindly; the slot must still end flat.
Upstream gives
A market exit ending REJECTED or CANCELLED (from the broker, or made up by Safety's repair), and the position on the next bar. Judging on the next bar lets a leg fill, for which the broker refused the joined exit, be booked first.
Algorithm
  1. If the slot is still in position on the next bar, log CRITICAL and send no further exit.
  2. Report "flatten wanted" until the flatten ends; Strategy then calls the flatten with reason exit_failed on each bar (feature 11).
  3. If that market order fails too, do not resend it; log CRITICAL.
Parameters
None.
Invariant
A slot never resends an exit that already failed in position; there is no retry counter.

EXECUTION_CLASSESEvery execution class by name (subclasses register themselves).

ExecutionConfigErrorThe slot's execution block is invalid; raised while the slot is built, so startup fails before trading.

Decisions already made

2One class or several?

Subclasses. ProtectedStrategyExecution, built only for slots whose execution block names it (decision 21), owns the broker group and the mask. The base class takes no resting exits and masks nothing: masking without a broker order is never safe, so it lives only where the order is placed.

3How does outside code learn the phase?

One question, is_processing_order(), reached only through Strategy; plus is_quarantined(). Safety's repair picks slots by their submitted or open orders, asking is_processing_order() only to decide whether a slot with no orders deserves a warning.

Rejected: reading state names, which a subclass's new phases would silently escape; order questions on this component — they belong to Order Manager.

4How does it learn that a group is closed?

It asks Order Manager directly.

Rejected: Strategy relaying an order context, and tracking orders itself.

5Which sample?

The system golden sample for the base class plus a component-level protected sample. The join-vs-fill race lives here, not in Order Manager.

6A protective leg rejected or cancelled by the broker without our request?

No retry. The trade falls back to bar-close market exits for every condition; its market exits still join the group while a leg survives, and go out plain once every leg is dead.

Rejected: a live retry (cancel the rest, wait, place a fresh group) — more states for a rare event.

7Is a new group ever placed in a trade?

No. A market exit joins the working group instead (decision 16). Moving an existing working order into a group is refused by IBKR (errors 10326/10327) and is not used.

8Stop already crossed when protection would be placed?

Place no group; the trade runs unprotected and exits through the normal bar-close market exit.

Rejected: an immediate market exit.

9Entry partially filled?

Place protection only once the entry order is closed, sized to its total filled quantity; nothing for a zero fill.

10Which conditions are masked?

Selected conditions, and only in IN_POSITION_PROTECTED (every leg OPEN). While placing and after a fallback, every condition is judged at bar close; a market exit there is safe because it joins the group.

11Who enforces "an exit never exceeds the position"?

StrategyExecution, from Order Manager's filled quantities. Order Manager sends what it is given.

13Does StrategyExecution hold the signal?

Yes (System map decision 20). It asks for entry or exit in the phase that needs the answer, reads its params through the signal, freezes and releases exit inputs, and logs the inputs with each decision.

14Where do per-condition exit answers and levels come from?

From the signal: evaluate_exit_conditions() returns each named condition's answer; exit_condition_level(name) returns the price the condition compares the close with. The entry price behind a level is the broker's average fill price. The protected class reads each selected level on the trade's first bar in position and stores none; a missing level places no group. The condition's direction and the slot's side give the leg's side; the Gateway rounds to tick.

Rejected: forcing selected conditions false inside the signal (it loses the fact that the condition really fired).

15A selected and a non-selected condition both fire on the same bar?

No market exit that bar: the selected condition means price crossed its level, so the broker order has exited or is exiting. A market exit on top would be refused rather than exit twice (decision 16), so this is a preference, not the safety rule. If the broker order did not fill, the non-selected condition is judged again next bar.

16How does a market exit avoid exiting twice while legs are working?

The MKT carries the trade's OCA group (type 2). Verified on an IBKR paper account: into a working group it filled and the broker stopped both legs first; into a group whose leg had filled, the broker refused it (Inactive + error 201), also when sent 0.2 ms after a marketable sibling — 5 of 5. This replaces cancel → wait for final → market and needs no closing state.

Not tested: the MKT reaching the broker before a sibling fills at the exchange; accepted as very unlikely.

17Which phases does the protected class add?

Two: PROCESSING_PROTECTION_ORDERS and IN_POSITION_PROTECTED. The base states keep their meaning; no closing state.

18After a fallback, is the surviving leg left working or cancelled?

Left working. It needs no cancel, no cancel outcome and no cancel-vs-fill race, and keeps a broker-side order in place. Later market exits join the group, so nothing exits twice; with no surviving leg they go out plain.

19How does a leg in the broker's pending-cancel state count?

It never reaches this component: the Gateway drops pending-cancel, and Order Manager enters CANCELLING only for a cancel the slot sent. An unrequested cancel is seen on its final Cancelled, which triggers the fallback. A CANCELLING leg is not open.

20Is the session-end flatten a signal exit?

No. Signal exits come from the signal (the protected class joins the OCA group); the flatten comes from outside the strategy (cancel all → wait for final → MKT → DONE, the same for every class). A rejected flatten order is not retried; the shutdown flat check is the backstop.

21How does a slot pick its execution class?

Explicitly, by name, in the slot's execution block: execution: {class: ProtectedStrategyExecution, resting_exits: {...}}. The other keys are that class's options; no block builds the base class. Anything invalid fails startup naming the slot.

Rejected: inferring the class from an option; dropping an invalid block with a log line — a slot believed protected at the broker but not is exactly the risk the feature exists to remove.

22A disaster stop without masking?

StopLossProtectedStrategyExecution: one STP at a named level ± an offset in points. Every exit stays a bar-close market order that joins the group; the stop is there for when the server is down.

23What does StrategyExecution read from the signal besides its answers?

Only public methods: entry_conditions() for the entry log; exit_condition_names(), condition_names() and has_level() to check the execution block at startup; params for session, direction and the daily quota. It never reads the signal's private state (StrategySignal decision 8).

Rejected: reading the signal's logic structure or value cache directly.
