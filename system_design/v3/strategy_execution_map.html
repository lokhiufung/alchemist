StrategyExecution

The decision state machine inside each slot. It knows which phase the slot is in, asks the signal only the question that phase needs, sends only the orders that phase allows, and decides what each order event means.

v3 draft, 2026-11-06 — not agreed. Behaviours 1–12 and decisions 1–22 are settled. The calls on the signal use the v3 signal interface. 2026-11-07: startup checks and the entry log read the signal only through its public methods (decision 23).

StrategyExecution · Goal

Goal

Each strategy slot moves through its execution phases correctly and sends only the entry and exit orders those phases allow. For a protected slot, it also never sends a market exit outside the trade's OCA group while a protective order may still fill, and never leaves an open position without protection it has not accounted for.

StrategyExecution · What this component does

What this component does

Strategy hands it every completed bar and every order update.

On a bar, it asks the signal whether to enter or exit — only the question its phase needs — and, when the phase allows, sends entry or exit orders and cancels to Order Manager. It freezes the signal's exit inputs on the entry-decision bar and releases them when the slot is flat again.

On an order update, it decides what the event means in the current phase. It asks Order Manager — which it already holds to send orders — for what it needs: the order's status and filled quantity (get_order), the group's submitted and open orders, and whether the group is closed (is_group_closed).

The trade's position is the entry order's filled quantity minus its exit orders' filled quantity, all from Order Manager.

A failed exit (rejected or cancelled while in position) is never sent again: on the next bar the slot flattens instead (behaviour 12).

Three classes, one contract

ClassExits
StrategyExecution (base)Bar-close market entries and exits. Knows nothing of resting exits: every exit condition exits at bar close.

Falls back to bar-close market exits when protection is lost; once every leg is dead they go out as plain market orders.

StrategyExecution · Behaviours

Behaviours

1Base lifecycleboth classes

Given
Bars and order updates on a base-class slot.
Must
Stay flat until the entry signal, then decide one entry. On its fill, be in position. On a bar-close exit signal, decide one exit. On its fill, be flat, count the round trip, and stop at the daily cap. A dead entry returns to entry seeking; a dead exit returns to in position. Freeze the signal's exit inputs on the entry-decision bar, before the entry order is sent; release them on the exit fill or when the entry dies.
Invariant
At most one order in flight; no order after the cap; a trade's frozen inputs are never released while it is open.

2The processing-order questionboth classes

Given
is_processing_order(), asked through Strategy by Safety's repair, the Event Loop and shutdown.
Must
Answer true while the slot waits on an order's outcome before it can move on: PROCESSING_ENTRY_ORDER or PROCESSING_EXIT_ORDER, and for a protected slot also PROCESSING_PROTECTION_ORDERS; in SESSION_END_FLATTENING, only while an order of the slot may still fill. False in every other phase, including IN_POSITION_PROTECTED (a position with its legs resting).
Invariant
The only phase questions asked from outside are this one and is_quarantined() (behaviour 10), and no caller reads state names. Questions about orders are answered by Order Manager, not here.

3Protect on entryprotected

Given
The first bar in position after the entry order is closed with filled quantity > 0. Placement is bar-driven: the level needs the actual average fill price, and the order-update handler is synchronous so it cannot await a group placement.
Must
Once per trade:
  • Take the selected levels for the actual average fill price, from exit_condition_level (decision 14).
  • If no level is available, or the stop is already crossed by the latest close, run this trade unprotected (stay in IN_POSITION_ACTIVITY).
  • Otherwise request one group of the selected legs, sized to the filled quantity, under a fresh OCA group, and enter PROCESSING_PROTECTION_ORDERS. When every leg is OPEN, enter IN_POSITION_PROTECTED.

Stop-loss class: the level comes from the signal's level(name) moved by the offset against the trade (long: below, short: above); one STP leg (decision 22).

Invariant
Protection is sized to the confirmed filled quantity; at most one group per trade; no group for a zero fill or a crossed stop.

4Maskingprotected only · the base class masks nothing

Given
A completed bar while in position, and the signal's per-condition answers from evaluate_exit_conditions() (decision 14).
Must
  • In IN_POSITION_PROTECTED: send a bar-close market exit only when a non-selected condition is true and no selected condition is true. When a selected condition is true, send no market exit that bar, even if a non-selected one is also true (decision 15), and log it.
  • In PROCESSING_PROTECTION_ORDERS and IN_POSITION_ACTIVITY: judge every condition at bar close (decision 10).
  • Log every raw condition answer.
  • Stop-loss class: masking does not apply; every condition is judged at bar close in every phase.
Invariant
On every bar of an open position, each selected condition is covered by a working leg or by bar-close evaluation.

5A market exit joins the groupprotected

Given
A market exit decision from the signal while the trade has a group with at least one leg still submitted or open. With every leg dead the exit is a plain market order: nothing is left to cancel, and a bad group must not also block the exit. The session-end flatten is behaviour 11, not this.
Must
Send one market order sized to the trade's position, carrying the group's OCA group and OCA type 2, with no cancel before it, and enter PROCESSING_EXIT_ORDER. The broker either fills it and cancels the legs, or refuses it when a leg already filled (at IBKR: Inactive + error 201, normalised to REJECTED).
  • On its fill: complete the round trip.
  • On its reject or cancel: if the slot is flat, a leg fill has already closed the trade (behaviour 6); otherwise return to IN_POSITION_PROTECTED when every leg is still OPEN, else to IN_POSITION_ACTIVITY, and the exit counts as failed (behaviour 12).
Invariant
No market exit outside the group while a leg may still fill; no cancel comes before a market exit; a market exit never exceeds the trade's position from Order Manager's filled quantities.

6Resting fillprotected

Given
A protective leg execution that reduces the position, in any phase of the trade.
Must
Interpret each update by the order it is for (entry, exit, or a leg of the trade's group), not by the current phase. When the position is flat, complete the round trip exactly like a bar-close exit (count, release the frozen inputs, daily cap → done) without any market order. A later update for an order of a closed trade (the sibling's Cancelled, a refused MKT) changes no phase.
Invariant
Every fill that makes the slot flat completes exactly one round trip.

7Lost protectionprotected

Given
A leg ends Rejected or Cancelled while the position is open — and not because the trade's own market exit joined the group or a sibling filled.
Must
No re-placement: enter IN_POSITION_ACTIVITY and judge every condition at bar close from then on. Later market exits still join the group while a leg survives, and go out plain once none does. Log at CRITICAL. The surviving leg is left working (decision 18).
Invariant
At most one group per trade.

8Gating and daily rolloverboth classes

Given
Bars before warmup is ready, outside the session (including holiday half-sessions), or on a new trading date.
Must
Seek entries only while warmup is ready and the bar is in session, per the instrument's exchange profile (a half-session holiday counts as closed; if the calendar is unavailable, fall back to open). On the first bar of a new trading date (overnight sessions: at the session roll, not midnight), reset the round-trip count and let a done slot trade again, without disturbing an open position.
Invariant
No entry order while not warm or out of session.

9Round-trip count across a restartboth classes

Given
A restart in the middle of a trading date, with a round-trip store.
Must
Persist the count on each completed round trip and on the daily reset. On restart in session, restore the same-day count and park in DONE when it is at or over the cap. With no store, no record, or outside session, start from zero.
Invariant
A restart never lets the slot exceed its daily cap.

10Error parkingboth classes

Given
The slot has been quarantined (ERROR).
Must
Stay in ERROR and place no order on every bar. Log a reminder at most once per interval per quarantine, saying how long the slot has been parked. On release, restart from waiting for working hours — except a slot quarantined while done (at its daily cap), which returns to done while the trading date is the same.
Invariant
An ERROR slot never sends an order; a quarantine and release never lets the slot exceed its daily cap.

11Session-end flattenboth classes

Given
request_flatten from outside the strategy (the shutdown coordinator at a session's cutoff, or SIGINT), in any state — or from Strategy with reason exit_failed (behaviour 12).
Must
Enter SESSION_END_FLATTENING and, on each call:
  • cancel every open order;
  • while Order Manager has a submitted, open or cancelling order, wait;
  • when flat, go to DONE;
  • otherwise send one market order for the booked position (no OCA group).
A rejected flatten order is not resent (same trading date, even across a quarantine). While flattening, no bar is handled and no order update changes the state; the flatten fill counts no round trip.
Invariant
No market order while an order of the slot may still fill; at most one flatten market order per trading date; the same rule for every class.

12Failed-exit flattenboth classes

Given
A market exit of the slot ends REJECTED or CANCELLED (a broker reject, or one made up by Safety's repair) and, on the next bar, the slot is still in position. Judging on the next bar lets a leg fill that the broker refused the joined exit for be booked first.
Must
  • Log CRITICAL and send no further exit.
  • Report flatten_wanted() until the flatten ends; Strategy then calls request_flatten('exit_failed') with the booked position on each bar (behaviour 11: cancel all, wait, one plain market order, DONE for the trading date).
  • If that market order fails too, it is not resent and is logged CRITICAL.
Invariant
A slot never re-sends an exit that has already failed in position; there is no retry counter.

StrategyExecution · Decisions already made

Decisions already made

2One class or several?

Subclasses. ProtectedStrategyExecution, built only for slots whose execution block names it (decision 21), owns the broker group and the mask. The base class takes no resting exits and masks nothing: masking without a broker order is never safe, so it lives only where the order is placed.

3How does outside code learn the phase?

One question, is_processing_order(), reached only through Strategy; plus is_quarantined(). Safety's repair picks slots by their submitted or open orders, asking is_processing_order() only to decide whether a slot with no orders deserves a warning.

Rejected: reading state names, which a subclass's new phases would silently escape; order questions on this component — they belong to Order Manager.

4How does it learn that a group is closed?

It asks Order Manager directly.

Rejected: Strategy relaying an order context, and tracking orders itself.

5Which sample?

The system golden sample for the base class plus a component-level protected sample. The join-vs-fill race lives here, not in Order Manager.

6A protective leg rejected or cancelled by the broker without our request?

No retry. The trade falls back to bar-close market exits for every condition; its market exits still join the group while a leg survives, and go out plain once every leg is dead.

Rejected: a live retry (cancel the rest, wait, place a fresh group) — more states for a rare event.

7Is a new group ever placed in a trade?

No. A market exit joins the working group instead (decision 16). Moving an existing working order into a group is refused by IBKR (errors 10326/10327) and is not used.

8Stop already crossed when protection would be placed?

Place no group; the trade runs unprotected and exits through the normal bar-close market exit.

Rejected: an immediate market exit.

9Entry partially filled?

Place protection only once the entry order is closed, sized to its total filled quantity; nothing for a zero fill.

10Which conditions are masked?

Selected conditions, and only in IN_POSITION_PROTECTED (every leg OPEN). While placing and after a fallback, every condition is judged at bar close; a market exit there is safe because it joins the group.

11Who enforces "an exit never exceeds the position"?

StrategyExecution, from Order Manager's filled quantities. Order Manager sends what it is given.

13Does StrategyExecution hold the signal?

Yes (System map decision 20). It asks for entry or exit in the phase that needs the answer, reads its params through the signal, freezes and releases exit inputs, and logs the inputs with each decision.

14Where do per-condition exit answers and levels come from?

From the signal: evaluate_exit_conditions() returns each named condition's answer; exit_condition_level(name) returns the price the condition compares the close with. The entry price behind a level is the broker's average fill price. The protected class reads each selected level on the trade's first bar in position and stores none; a missing level places no group. The condition's direction and the slot's side give the leg's side; the Gateway rounds to tick.

Rejected: forcing selected conditions false inside the signal (it loses the fact that the condition really fired).

15A selected and a non-selected condition both fire on the same bar?

No market exit that bar: the selected condition means price crossed its level, so the broker order has exited or is exiting. A market exit on top would be refused rather than exit twice (decision 16), so this is a preference, not the safety rule. If the broker order did not fill, the non-selected condition is judged again next bar.

16How does a market exit avoid exiting twice while legs are working?

The MKT carries the trade's OCA group (type 2). Verified on an IBKR paper account: into a working group it filled and the broker stopped both legs first; into a group whose leg had filled, the broker refused it (Inactive + error 201), also when sent 0.2 ms after a marketable sibling — 5 of 5. This replaces cancel → wait for final → market and needs no closing state.

Not tested: the MKT reaching the broker before a sibling fills at the exchange; accepted as very unlikely.

17Which phases does the protected class add?

Two: PROCESSING_PROTECTION_ORDERS and IN_POSITION_PROTECTED. The base states keep their meaning; no closing state.

18After a fallback, is the surviving leg left working or cancelled?

Left working. It needs no cancel, no cancel outcome and no cancel-vs-fill race, and keeps a broker-side order in place. Later market exits join the group, so nothing exits twice; with no surviving leg they go out plain.

19How does a leg in the broker's pending-cancel state count?

It never reaches this component: the Gateway drops pending-cancel, and Order Manager enters CANCELLING only for a cancel the slot sent. An unrequested cancel is seen on its final Cancelled, which triggers the fallback. A CANCELLING leg is not open.

20Is the session-end flatten a signal exit?

No. Signal exits come from the signal (the protected class joins the OCA group); the flatten comes from outside the strategy (cancel all → wait for final → MKT → DONE, the same for every class). A rejected flatten order is not retried; the shutdown flat check is the backstop.

21How does a slot pick its execution class?

Explicitly, by name, in the slot's execution block: execution: {class: ProtectedStrategyExecution, resting_exits: {...}}. The other keys are that class's options; no block builds the base class. Anything invalid fails startup naming the slot.

Rejected: inferring the class from an option; dropping an invalid block with a log line — a slot believed protected at the broker but not is exactly the risk the feature exists to remove.

22A disaster stop without masking?

StopLossProtectedStrategyExecution: one STP at a named level ± an offset in points. Every exit stays a bar-close market order that joins the group; the stop is there for when the server is down.

23What does StrategyExecution read from the signal besides its answers?

Only public methods: entry_conditions() for the entry log; exit_condition_names(), condition_names() and has_level() to check the execution block at startup; params for session, direction and the daily quota. It never reads the signal's private state (StrategySignal decision 8).

Rejected: reading the signal's logic structure or value cache directly.
