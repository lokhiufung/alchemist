Event Loop

The engine's heartbeat. It drains one shared queue of events, packs ticks into 1-second bars, and hands every bar and order update to the right strategies — in time order, exactly once — while keeping one broken strategy from stopping the rest.

v3 draft, 2026-11-08 — not agreed. Behaviours 1–10 and decisions 1–4 are settled. Behaviours 11–19 and decisions 5–10 are proposed. Multi-asset: sessions and cutoffs follow each instrument's exchange profile, each on its own clock.

Event Loop · Goal

Goal

Take events from the queue, resample raw ticks into completed fixed-interval OHLCV bars, and deliver completed bars, order updates and balance updates to the strategies that subscribe to them — strictly in time order, exactly once, and with strong fault isolation.

Owns, from the System map:

Turning ticks into completed bars and delivering bars and order updates to the right strategies, in time order, exactly once; and seeding each strategy with the broker warmup history it needs (daily and prior-session), fetched through Gateway and retried until it lands (System map decision 23; auxiliary series move to Aux Data, decision 44, proposed).

Event Loop · What this component does

What this component does

The Event Loop is the central processing engine. It drains these events from the shared queue: tick, bar, order_update, balance_update, repaired_fill and end_of_data.

JobHow
Make barsA resampler per instrument gathers prices and volumes into 1-second OHLCV bars. A bar is finished when the next second starts, or — in quiet periods — when the clock-driven flush grace forces it out.
DeliverSends completed bars to the strategies on that instrument, and order updates to all strategies, so session-end closing fills are always booked.
IsolateA strategy that keeps throwing errors is quarantined; the others carry on.
SeedFetches broker warmup history for each strategy before it trades, and retries until it lands.
FlattenAt each session's cutoff, asks that session's strategies to go flat.
RecordIn live and paper modes, writes bars and trades to disk.
ReconcileRuns a periodic check for strategies stuck waiting on an order.
Event Loop · Load and event buffer

Load and event buffer

This section states the load one process must carry, where that load costs time, and how the event buffer tells the drain loop that there is work. Behaviour 11 and decisions 8–10 are the contract; this section explains them.

Load target

ItemTargetWhy it matters
Tick streams3 simultaneous IB reqTickByTickData streamsIB allows tick-by-tick streams equal to 5% of the account's market data lines (about 5 at 100 lines), and 1 request per instrument every 15 s. Options have no tick-by-tick data, so an option instrument needs another feed type.
Strategies10–15 active at the same time, in one processThis is more than the "about 10" that System map decision 28 gives for one process. The fan-out (below) sets the real limit.
Ticks per secondNot known yet. Measure the peak from recorded tick data (market open, news).No IB message-rate cap and no trusted ES peak figure was found. The design must not depend on a guessed rate.
Bars per second after resamplingAt most 3 (one 1-second bar per stream)A tick burst never reaches the strategies. They see bars only.
Latency5 ms end-to-end at p99 (System map R3, decision 25)Queue wait, GIL wait and the sum of slot costs all count against it.

Two problems, not one

Ingest: producers append to two lanes and the drain loop folds ticks into bars. Fan-out: each bar steps the strategies on its instrument one after another.

LayerWhat costs timeAnswer in this design
IngestA wake-up per event; a fill waiting behind queued ticks; the IB reader thread decoding in pure Python while it holds the GIL, so the loop thread can wait up to the GIL switch interval (5 ms by default, about 10 ms in the worst case).One wake-up per burst, a control lane drained first, a batch budget (behaviour 11, decision 8); a 0.5 ms switch interval (decision 10).
Fan-outStrategies on one bar run one after another, so dispatch latency is the sum of their slot costs. Example: 300 µs × 15 strategies = 4.5 ms, which alone breaks R3.Measure the summed slot cost per instrument (behaviour 14). Above the scale trigger, move to strategy node processes (decision 9).

Drain wake-up

The drain loop is the only consumer. When both lanes are empty it sleeps on drain_wakeup and uses no CPU. A producer that appends an event wakes it, so the drain starts at once and not on the next 20 ms timer tick.

A producer on another thread cannot set the event directly. It calls loop.call_soon_threadsafe(drain_wakeup.set), which takes a lock, puts the callback on the loop's ready list and writes one byte to a pipe (one system call). The loop then reads the byte, runs the callback and resumes the drain.

The rule: a producer sends a wake-up only when no wake-up is already pending. While the loop is awake and draining, it will see the new event anyway, so another wake-up is wasted work that also takes GIL time from the loop. Example: a burst of 1,000 ticks.

TimeReader threadDrain loopWake-up sent?
t0append tick 1asleepYes — the loop is asleep
t0 + 5 µsappend tick 2waking upNo — a wake-up is pending
t0 + 50 µsappend ticks 3–40drains ticks 1–40No — the loop is awake
…append ticks 41–1000keeps drainingNo
end—both lanes empty, goes to sleep—
laterappend tick 1001asleepYes

The burst costs 2 wake-ups instead of 1,001.

The race rule: the consumer clears wake_pending before it drains, never after. If it cleared the flag after the drain, this could happen:

  1. The consumer pops the last event and sees both lanes empty.
  2. The producer appends a fill, sees wake_pending still set, and sends no wake-up.
  3. The consumer clears wake_pending and goes to sleep.
  4. The fill waits in the buffer until the 20 ms timeout fires.

When the flag is cleared first, the worst case is one extra wake-up that finds an empty buffer, which is harmless. The flag needs no lock: an extra wake-up costs nothing, and a missed one is caught by the 20 ms timeout, which also runs the clock-driven bar flush (behaviour 2).

Lanes and batch budget

  • Control lane: order_update, balance_update, repaired_fill, book operations, end_of_data. Data lane: tick, bar.
  • Each drain pass empties the control lane first, then takes data events. A fill never waits behind a tick burst. Replay already puts fills at the front of the buffer, so live and replay follow one rule (System map decision 46).
  • A pass stops after the batch budget (2 ms) and yields, so the bar flush, reconcile and book operations run on time. Events left over are drained in the next pass, with no new wake-up needed.
  • Arrival order holds within each lane. Per-instrument bar order (behaviour 3) is not affected, because ticks and bars all use the data lane.
Event Loop · Sample

Sample

The Event Loop's slice of the system golden sample from the System map.

InputA time-ordered stream of 1-second ticks for one instrument from the Gateway, two order fills (BUY on the bar that crosses level L, SELL on the target T bar), then an end_of_data event.
ExpectedEach 1-second bar reaches the strategy exactly once, in time order. Both order updates reach the strategy as soon as they are taken off the queue. The loop ends cleanly on end_of_data.
Passes whenThe strategy gets every completed bar in sequence, with no duplicate or missing timestamps; gets both fills; and the loop ends with no unhandled exception.
Fails whenA bar is delivered out of order, skipped, or more than once; an order update is dropped; an unhandled exception in one strategy stops bars reaching the others; or the loop keeps running after end_of_data.
Event Loop · Behaviours

Behaviours

Each behaviour says what the Event Loop is given, what it must do, and what must always stay true.

1Ticks become OHLCV bars

Given
A sequence of tick events for a subscribed instrument.
Must
Gather ticks into fixed 1-second OHLCV bars and emit a completed bar when the time bucket rolls over.
Invariant
A bar's OHLC reflects every tick in [timestamp, timestamp + resolution), and its volume is exactly the sum of the tick sizes.

2Clock-driven bar flush

Given
An open bar bucket whose time closed more than the flush grace (1.0 s) ago, with no tick arriving to roll it over.
Must
Force the in-progress bar into the event queue, using its last known price as the close.
Invariant
Bar delay in quiet periods has a hard cap. Ticks that arrive later for an already-emitted bucket are safely ignored.

3Bars delivered strictly in order

Given
A completed OHLCV bar for an instrument.
Must
First let Aux Data add its values to the bar (Aux Data behaviour 7), then tell the Gateway (on_bar, which drives simulated fills), then call on_bar on every strategy registered to that instrument, in time order.
Invariant
Strategies get bars in non-decreasing timestamp order, exactly once per bar interval.

4Order and balance updates go to everyone

Given
An order_update, balance_update or repaired fill event from the buffer.
Must
Send the update to all active strategies, and trigger a trade-recorder flush when a round trip closes.
Invariant
Every strategy gets order updates whatever its session state, so fills for closing or session-end orders are never dropped.

5Error isolation and quarantine

Given
A strategy's on_bar keeps throwing uncaught exceptions, past the quarantine threshold (3 in a row).
Must
Log the failure, put that strategy into the ERROR state, and keep running normally for all the other strategies.
Invariant
An error or crash in one strategy never crashes the main loop or gets in the way of other strategies.

6Periodic check for stuck strategies

Given
A regular interval (for example every 60 s).
Must
Ask the broker, through the Gateway, for executions and open orders, and run Safety's repair for any strategy that reports it is processing an order.
Invariant
This check runs asynchronously and never blocks or slows real-time bar processing.

7Clean shutdown

Given
An end_of_data event in replay, or a trigger from the shutdown coordinator in live mode.
Must
Flush any buffered bars, drain the disk recorders, tell the strategies, and leave the loop.
Invariant
On a normal shutdown no queued event is left unprocessed, and every recorded bar and trade file is fully closed.

8Warmup seeding and retry

Given
Strategies starting up, or a slot whose seed failed.
Must
  • Request, through the Gateway, each strategy's daily history (warmup window clamped to a min/max) and prior-session intraday bars — one fetch per key, shared between slots — and hand them to the strategy.
  • The Gateway builds the daily bars per session, with holidays, early closes and a contract roll (Gateway behaviour 7). The Event Loop only requests them, in live and in replay alike (System map decision 45).
  • Mid-session start: after the seeds, replay today's recorded bars.
  • Retry: a failed or empty fetch retries in the background with jittered, capped backoff until it lands (behaviour 18).
  • Failure scope: a failed required seed quarantines only that slot; a terminal quarantine stops its retry.
  • Auxiliary series are not seeded here: Aux Data owns them.
Invariant
A slot is never armed on a seed that did not land. One slot's seed failure never affects another slot.

9Session-end flatten

Given
The clock (live) or the replay clock reaching a session's cutoff, or a shutdown signal.
Must
  • At each session's own cutoff — early closes included, never at a session open or an evening start-up — ask each strategy of that session to flatten. The cutoff is one minute before the session's real end, on the session's own clock, from its exchange profile (for example CME day and overnight sessions in New York; Eurex day session 17:30 and overnight 22:00 Frankfurt).
  • Keep asking on every tick (every replayed bar in simulation) until the strategy is flat and idle, a SIGINT/SIGTERM arrives (one call, no wait), or 10 s pass.
  • A flattening slot gets no bars. Keep going when a flatten raises. Read no execution state.
  • When every slot has ended but none trades its exchange's continuous data session, keep the process running — still recording bars — until every configured exchange's data session has closed.
  • Before exit: cancel working orders on configured instruments and wait for them, then force-flatten any leftover position on a configured instrument that has no working order left; otherwise page and exit non-zero. If the open orders cannot be read, treat every configured instrument as still blocked — never force-flatten next to orders the engine could not see.
Invariant
At exit every configured position is flat or flagged. An instrument the engine does not trade is never touched. No market order is sent at shutdown on an instrument that still has, or may have, a working order.

10Recording

Given
Completed bars and fills in live/paper mode.
Must
Append every bar to the day's file per instrument (overnight sessions are not split at midnight) and roll it up at day end or on finalize. Pair fills into per-strategy round trips (weighted average prices for multi-fill legs) and flush them, with currency, repairing a pending commission later.
Invariant
A recorded bar is durable before finalize. Recording never blocks or changes trading.

Proposed · not agreed

11Drain on wake-upproposed · System map decision 26 · decision 8

Given
A producer (the broker's reader thread, the bar flush, Safety's repaired fills) has appended to the event buffer.
Must
  • Append to the control lane (order_update, balance_update, repaired_fill, book operations, end_of_data) or the data lane (tick, bar).
  • After appending, raise the drain wake-up only if wake_pending is clear, and set it. A producer on another thread raises the wake-up only through the loop (call_soon_threadsafe).
  • The drain loop clears the wake-up and wake_pending before it starts a drain pass, never after.
  • Each pass empties the control lane first, then takes data events, and yields after the batch budget (2 ms). Events left over go to the next pass without a new wake-up.
  • Wait on the wake-up with a 20 ms timeout, so the clock-driven bar flush (behaviour 2) still runs on its cadence when no event arrives.
  • Replay preloads the whole day and puts fills at the front of the buffer.
Invariant
Queue wait is close to 0 instead of 0–20 ms. A burst costs one wake-up, not one per event. An event appended while a pass ends is never left waiting for the timeout. Events are drained in arrival order within each lane, each exactly once.

12Backlog alarmproposed · System map decision 27 · refines decision 3

Given
A drain pass.
Must
Log the buffer size and the pass's p99 queue wait. Above the backlog threshold, raise an ERROR with an operator alert.
Invariant
No event is ever dropped; decision 3 holds.

13One dispatch pathproposed

Given
An event popped from the event buffer, in the main drain or in the final drain after the loop has stopped.
Must
  • Dispatch it through one table, HANDLERS, keyed by event type, in both places. A new event type is one new entry.
  • Fan an event out to strategies through one helper, fan_out(strategies, method, payload), for bars, order updates and balance updates alike. It logs each strategy's exception and keeps the quarantine count (behaviour 5).
  • Emit every completed bar through one function, emit_bar(instrument, bar, source): a tick rollover, the clock-driven flush and the end-of-data flush all use it, and it writes the one bar latency record.
Invariant
A new event type is handled the same way during and after the session. There is one place that catches a strategy's exception, and one place that makes a bar.

14Latency budgetproposed · System map decisions 25, 28, 29

Given
The strategies on an instrument and a completed bar for it.
Must
  • Log end-to-end latency (closing tick's broker timestamp → order leaving the Gateway, System map R3) next to dispatch latency and slot cost, and keep per-bar disk writes off the loop thread.
  • Log, per minute as p50/p99, the summed slot cost of the strategies on each instrument and the IB reader thread's decode time. These two numbers drive the scale trigger and the Gateway choice in decision 9.
  • A rebuild replaying seed bars yields within a time budget, not a fixed chunk, so live bars for other slots are not held behind it.
Invariant
Strategies on a bar are still stepped one after another in time order.

15One runtime book, changed only between eventsproposed · System map decision 34

Given
The strategies the process runs and the resources serving them, at cold start or while running.
Must
  • Hold them in one runtime book: strategies (dispatch order), resamplers and bar buffers per signal instrument, contracts (every signal and execution instrument), the fed instruments, sessions by instrument, by strategy and by execution instrument, and retry tasks. Each container is made once and changed in place, so a holder of a reference (the recorders) sees additions without being told.
  • Reserve an instrument before any strategy on it is committed: resampler, bar buffer, contract and recording partition. Reserving is idempotent; a partition already set is kept, so a shared instrument's bar files are never re-bucketed.
  • commit(strategy, retry_tasks) is synchronous: it appends the strategy and sets its session maps in one call, or raises on a duplicate strategy key and leaves the book unchanged.
  • Only the drain-loop task reserves, releases or commits. Another task calls enqueue_book_op(fn) and awaits its future; the drain loop pops the book operation like any event, runs fn(book) and resolves the future with the result or the exception (logged; draining continues).
  • A book operation enqueued after shutdown was requested is refused at once; one still queued when the loop stops fails with "book closed"; a cancelled one is skipped. Events still queued for a released instrument are dropped.
  • Cold start: resolve contracts, reserve every instrument, subscribe, stage every slot, prepare, commit each, then build Safety, the freeze detector and the shutdown coordinator on the book.
Invariant
A bar or order dispatch sees the same strategy list for its whole awaited run.

16Add a strategy while runningproposed · System map decisions 35, 36

Given
A deploy request for one strategy key, in paper or live, received on the runner's local socket.
Must
  • Pre-flight (nothing exists yet, so a refusal cleans nothing): re-read the config in a worker thread and refuse stale_config, config_drift, unknown_key or conflict; import and construct the strategy in a worker thread (import_error, params_invalid); check the session gate (session_open, after_process_exit), the account route (unknown_account_route) and, from the broker's positions and open orders per account, any exposure no running strategy owns (unmanaged_exposure).
  • Reserve and subscribe: for each of the candidate's instruments not in the book, resolve the contract, reserve it through a book operation, and only then subscribe ticks for a new signal instrument. An execution-only instrument gets a contract and no feed. Re-declare the gateway's instrument sessions.
  • Prepare: run warmup on the candidate alone. A warmup fetch miss is not a failure: the normal retry runs and the strategy stays gated, as at cold start.
  • Commit through a book operation that re-checks shutdown and the session gate, then commits; reply registered.
  • A different request while one is in flight is busy; the same revision returns noop with the original request ID. After shutdown begins every request is shutting_down.
  • On a failure after pre-flight: cancel the candidate's retry tasks, unsubscribe and release only instruments no running strategy uses.
Invariant
Every outcome other than registered leaves the book as it was. Strategies already running keep their connection, positions, orders, indicators and partly built bars; no shared feed is dropped or re-subscribed.

17A committed strategy is a full memberproposed · System map decision 34

Given
A strategy committed after the process started.
Must
  • Get bars, order and balance updates from the next event, like any other strategy.
  • Session-end flatten (behaviour 9) uses its own session calendar: a day-session strategy added in the evening is first due at the next day-session close, not that evening.
  • Aux Data reads its members from the book on each step and arms a late joiner (Aux Data behaviour 9).
  • Bars are bucketed by the instrument's partition, fixed for the life of the process; trades by strategy key.
  • The deploy service stops before the retry tasks are cancelled, so a session-end exit cannot leave a staging task waiting on a stopped drain loop.
Invariant
No consumer keeps its own copy of the strategy list.

18One seed attempt, one retryproposed · decision 5

Given
A strategy to seed, at cold start, at hot-add or after a recoverable quarantine.
Must
  • Run one function, Seeder.attempt(strategy): fetch the daily history and the prior-session bars through one shared fetch (one lock and one time-to-live per key), then hand them to the strategy in its fixed order, and return the slot's new seed state.
  • At start, run one attempt per slot. Any result other than READY starts Seeder.retry(strategy), which runs the same attempt under one Backoff(base, max, jitter).
  • Keep at most one retry task per slot, held in the runtime book. A failed daily fetch and a failed seed are retried by the same task.
  • Hold the slot's seed state as one value: PENDING, READY, QUARANTINED_RECOVERABLE or QUARANTINED_TERMINAL. Re-read it after every await; a terminal state ends the retry and is never overwritten.
Invariant
Startup, warmup retry and seed recovery run the same code. Two tasks never seed one slot. A slot is READY only after its seed landed.

19No mode branchesproposed · System map decision 46

Given
Any run mode: replay, paper or live.
Must
  • Read the time only from the Clock it is given: the bar flush, the session-active flag, the reconcile interval and session-end flatten (behaviour 9) all use clock.now(), and the drain waits with clock.wait(). In replay, ReplayClock moves forward on each bar close.
  • Take recorders, Safety and the state stores as objects; in replay the runner passes do-nothing versions.
Invariant
No Event Loop code reads the run mode or checks a collaborator for None. Replay and live run the same lines.

"""Skeleton contract for the Event Loop component (Alchemist v3, draft)."""

from __future__ import annotations

import asyncio
import enum
from collections import deque
from typing import Any, Awaitable, Callable

from alchemist.clock import Clock
from alchemist.instruments import Instrument

ON_BAR_ERROR_QUARANTINE = 3       # Behaviour 5
BAR_FLUSH_GRACE_S = 1.0           # Behaviour 2, decision 2
ORDER_CHECK_INTERVAL_S = 60.0     # Behaviour 6
FLATTEN_WAIT_MAX_S = 10.0         # Behaviour 9
DRAIN_TIMEOUT_S = 0.020           # Behaviour 11
DRAIN_BATCH_BUDGET_S = 0.002      # Behaviour 11, decision 8
GIL_SWITCH_INTERVAL_S = 0.0005    # decision 10
SCALE_TRIGGER_SLOT_SUM_P99_S = 0.003  # decision 9
BACKLOG_ALERT = 5000              # decision 3, Behaviour 12

CONTROL_EVENTS = frozenset({"order_update", "balance_update", "repaired_fill",
                            "book_op", "end_of_data"})


class SeedState(enum.Enum):
    """Behaviour 18."""
    PENDING = "pending"
    READY = "ready"
    QUARANTINED_RECOVERABLE = "quarantined_recoverable"
    QUARANTINED_TERMINAL = "quarantined_terminal"


class Backoff:
    """Behaviour 18: jittered, capped delay; never shorter than base."""
    def __init__(self, base_s: float, max_s: float, jitter: float) -> None: ...
    def next_delay(self) -> float: ...


class SharedFetch:
    """Behaviour 18: one in-flight fetch per key, kept for a time-to-live."""
    async def get(self, key: tuple, fetch: Callable[[], Awaitable[Any]]) -> Any: ...


class Seeder:
    """Behaviours 8, 18."""
    async def attempt(self, strategy) -> SeedState: ...
    async def retry(self, strategy) -> None: ...


HANDLERS: dict[str, Callable[[dict], Awaitable[None]]] = {}   # Behaviour 13


async def fan_out(strategies: list, method: str, payload: Any) -> None:
    """Behaviours 4, 5, 13: call method on each strategy; log and count exceptions."""


async def emit_bar(instrument: Instrument, bar: dict, source: str) -> None:
    """Behaviours 1, 2, 13: the one place a completed bar enters dispatch."""


class Resampler:
    """Behaviours 1-2: ticks -> completed 1-second OHLCV bars."""
    def update_from_tick(self, ts: float, price: float, size: float) -> dict | None: ...
    def flush_due(self, now: float) -> dict | None: ...


class RuntimeBook:
    """Behaviours 15, 17: the one registry of strategies and per-instrument resources."""
    strategies: list                     # dispatch order
    resamplers: dict[Instrument, Resampler]
    bars: dict[Instrument, deque]
    contracts: dict[Instrument, Any]
    sessions_by_instrument: dict[Instrument, str]
    def reserve_instrument(self, instrument: Instrument, contract: Any) -> None: ...
    def release_instrument(self, instrument: Instrument) -> None: ...
    def commit(self, strategy, retry_tasks: list) -> None: ...
    def strategies_for(self, instrument: Instrument) -> list: ...


async def enqueue_book_op(fn: Callable[[RuntimeBook], Any]) -> Any:
    """Behaviour 15: run fn(book) on the drain loop between events."""


class EventBuffer:
    """Behaviours 11-12, decision 8: two lanes, one wake-up per burst."""
    control: deque
    data: deque
    wake_pending: bool
    drain_wakeup: asyncio.Event

    def push(self, event: dict) -> None:
        """Append to its lane; wake the loop only if no wake-up is pending."""
    def push_front(self, event: dict) -> None:
        """Replay: put a fill at the front of the control lane."""
    async def wait(self, clock: Clock) -> None:
        """Wait on drain_wakeup with timeout DRAIN_TIMEOUT_S."""
    def drain_pass(self, clock: Clock) -> list[dict]:
        """Clear the wake-up and wake_pending first; control events, then data
        events, until both lanes are empty or DRAIN_BATCH_BUDGET_S is spent."""
    def __len__(self) -> int: ...


async def run_event_loop(event_buffer: EventBuffer,
                         book: RuntimeBook, gateway, aux, safety,
                         recorders, shutdown, clock: Clock) -> None:
    """Behaviours 1-7, 11, 13, 19: set GIL_SWITCH_INTERVAL_S, drain on wake-up,
    resample, dispatch in time order exactly once, quarantine,
    reconcile, flatten, shut down cleanly."""

Event Loop · Decisions already made

Decisions already made

1Who gets order updates?

Every strategy. Each one filters by order-ID ownership, so a strategy that has just closed can still book its closing fill.

2How long can a quiet bar wait?

A 1.0 s clock-driven grace flush bounds the delay in illiquid periods without waiting for the next tick.

3Is the event queue bounded?

No — it is unbounded so order updates are never dropped. A backlog past 5000 items is reported (behaviour 12).

4When is a strategy quarantined?

After 3 consecutive on_bar exceptions it goes to the ERROR state, protecting the whole process.

Proposed · not agreed

5How many seeding paths are there?

One: Seeder.attempt(), run once at start and again by Seeder.retry(). A failed daily fetch and a failed seed are the same retry, with one shared fetch and one backoff. The slot's seed state is one value with four states (behaviour 18).

Rejected: a startup path plus separate warmup-retry and seed-retry loops (three copies of one sequence that drift apart); a cache that is used at start but not by retries.

6How is an event routed to its handler?

Through one table keyed by event type, used by the main drain and the final drain. Every fan-out to strategies goes through fan_out(), and every bar through emit_bar() (behaviour 13).

Rejected: an if/elif chain per drain, and a gather-and-log block copied for each update type.

proposed · 2026-11-07

7Is the resampler its own component?

No. It is a small pure module (ticks in, bars out, no I/O) under behaviours 1–2, tested alone. It stays out of the Gateway because the clock-driven flush needs the loop's clock and the broker's reader thread must stay thin (System map R3).

Rejected: a separate bar-building component (no outside input and no failure mode of its own); building bars in the Gateway.

proposed · 2026-11-07

8How does the event buffer wake the loop, and in what order does it drain?

One wake-up per burst: a producer raises the drain wake-up only when wake_pending is clear, and the drain loop clears the flag before each pass. The buffer has two deques: a control lane (fills, balance updates, repaired fills, book operations, end of data) drained first, and a data lane (ticks, bars). A pass yields after a 2 ms batch budget. The 20 ms timeout stays as a safety net and the bar-flush cadence (behaviour 11; Load and event buffer).

Rejected: a wake-up on every append (a lock and a system call per tick, almost all wasted during a burst); clearing the flag after the drain (a fill appended at the end of a pass waits up to 20 ms); one lane in arrival order (a fill waits behind a tick burst); one ring per tick stream with a round-robin drain (more parts for a fold that is already cheap, and it does not move decode off the GIL); a lock-free or shared-memory ring of the Disruptor kind (Python has no atomic operations, so its pure-Python versions use locks).

proposed · 2026-11-08

9What load must one process carry, and when do we scale?

One process carries 3 tick-by-tick streams and 10–15 strategies: one asyncio loop, the official IB reader thread, and the buffer of decision 8. Measure first (behaviour 14). Scale trigger: when p99 of the summed slot cost on the busiest instrument is above 3 ms (room left for feed transit inside R3's 5 ms), move to one Gateway process (IB socket, decoding, resampler, order send; System map decision 7 holds) plus strategy node processes of 5–8 strategies each, joined by a local socket or pipe. After resampling the bus carries only about 3 bars/s plus order updates. Shard by strategy group, not by instrument, because many strategies share each of the 3 instruments. Before that move, Safety and its repair need a design that covers every node (System map decision 28). Gateway trigger: if the reader thread's decode time or the GIL wait shows in p99 after decision 10, move the Gateway to an asyncio-native protocol with no reader thread.

Rejected for now: an asyncio-native Gateway with no reader thread (decoding then runs on the loop thread next to strategy work, and a reimplementation must follow IB's per-message move to protobuf); strategy node processes before the trigger fires (an extra hop for each bar and order, and Safety across nodes is not designed yet); free-threaded Python 3.14 (5–10% slower on one thread, and a C extension can turn the GIL back on).

proposed · 2026-11-08

10What GIL switch interval does the process use?

0.5 ms, set once at start with sys.setswitchinterval(0.0005). While the IB reader thread decodes a burst it holds the GIL, and at the default 5 ms the loop thread can wait that long (about 10 ms in the worst case), which is all of R3's budget. The cost is more thread switches; behaviour 14 measures whether it is enough (decision 9, Gateway trigger).

Rejected: keeping the 5 ms default (one GIL wait can use the whole latency budget); moving decoding off the GIL now (see decision 9).
