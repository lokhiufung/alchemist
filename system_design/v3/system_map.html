System map

The top-level boundary of the Alchemist v3 execution engine: what it is for, the components it is split into, what each one owns, and the one frozen example every component is tested against.

v3 draft, 2026-11-06 — not agreed.

v3 is a seven-component execution engine. Its first requirement is multi-asset and multi-currency trading (R1, decisions 37–41), and a signal is a Python SignalDag class that holds its own params, behind an abstract interface (decision 42).

Decisions 1–24 are settled. Decisions 25–47 are proposed and become agreed only once confirmed. Decision 44 proposes an eighth component, Aux Data.

System map · Goal

Goal

Execute a strategy book at the broker across asset classes (futures, stocks and options), instruments, exchanges and currencies, placing the same orders whether it runs on a simulated broker, a paper account or a live account.

Not this system's job

  • Strategy research: finding signals, fitting params, or any tooling that produces them.
  • Comparing the engine's trades with research results, and monitoring strategies for decay.
  • Keeping a registry of strategies and their params versions.
  • Version control of strategies and their params: the strategy code under local/strategies/ belongs to its author.
  • Portfolio reporting in a base currency (see decision 39).

System map · Introduction

Introduction

Alchemist v3 is an execution engine for strategies on futures, stocks and options. Its inputs are the broker's market data (or a replay source standing in for the broker), daily auxiliary series from outside data sources, plus deployment config supplied from outside and the author's strategy classes, which hold each signal's params. Its first book trades CME equity-index futures in USD and Eurex DAX futures in EUR. Its only consumer is the broker, which receives its orders.

  1. Market data enters through the Gateway.
  2. The Event Loop turns it into bars and dispatches them. Proposed: before dispatch, Aux Data adds daily auxiliary values from outside data sources to each bar, and tells each strategy that reads them whether it is ready.
  3. Each Strategy steps its StrategySignal and passes the bar to its StrategyExecution state machine, which asks the signal whether to enter or exit.
  4. The resulting orders are tracked by the Order Manager and leave again through the Gateway.
  5. Alongside, Safety watches the broker connection, reconnects it, and repairs any strategy left waiting on an order during an outage.

Every instrument names its exchange profile and currency, so every bar, order, fill and position knows where it trades and what money it is counted in.

System map · System boundary

System boundary

For each component: what it owns, what it leaves to others, what it receives, and what it produces.

Gateway

OwnsAll communication with the broker: market data in, orders and cancels out, fills and executions back, for every instrument the process trades. A replay source can stand in for the broker behind it.
Not its jobBuilding bars or deciding who hears an event (Event Loop); deciding what to trade (Strategy, StrategyExecution); tracking an order's life (Order Manager); noticing a dead connection or repairing strategies after one (Safety).
ReceivesFrom the broker: market data and fills. From Order Manager: orders and cancels. From Safety: heartbeat checks, reconnect requests, requests for executions. From the Event Loop: history requests for warmup.
ProducesTo the Event Loop: ticks, order updates and warmup history. To the broker: orders and cancels. To Safety: connection health and the broker's executions.

Event Loop

OwnsTurning ticks into completed bars and delivering bars and order updates to the right strategies, in time order, exactly once; and seeding each strategy with the warmup history it needs (daily, prior-session and auxiliary), fetched through Gateway — auxiliary series straight from outside data sources — and retried until it lands. Proposed (decision 44): auxiliary series and arming move to Aux Data.
Not its jobThe broker connection, and building daily bars from intraday history (Gateway); entry/exit decisions (Strategy, StrategyExecution); recovering from an outage (Safety).
ReceivesFrom Gateway: ticks, order updates and warmup history. From outside data sources: auxiliary daily series (proposed: none; Aux Data reads them). From Aux Data (proposed): values on each bar. From Safety: repaired fill events.
ProducesTo Strategy: completed bars, order updates and warmup history. To Gateway: history requests.
ProposedAlso owns the runtime book, the one registry of the strategies the process runs and the per-instrument resources serving them, and adding one strategy to it while the process runs (decisions 34–36). Receives, from the operator in paper/live: deploy requests. Produces, to the operator: one status line per step until a terminal status. Produces, to Gateway: contract, subscribe and unsubscribe requests for a new strategy's instruments.

Aux Data (proposed · decision 44)

OwnsReading auxiliary daily series from outside data sources, each through one data-source interface; deciding when a value is settled for its target session; arming and disarming each group of strategies that read them; adding the values to bars; and serving the history frames a cold rebuild needs.
Not its jobBroker history (Gateway, requested by the Event Loop); delivering bars (Event Loop); when a signal may be rebuilt and telling StrategyExecution it is ready (Strategy); how a calculation is seeded (StrategySignal).
ReceivesFrom outside data sources (files in replay): auxiliary daily series. From the Event Loop: each completed bar before dispatch, and the runtime book's members. From Strategy: frame requests on a cold rebuild.
ProducesTo the Event Loop: bars with auxiliary values added. To Strategy: ready / not ready, with the history frames.

Strategy

OwnsBeing the one per-slot object the Event Loop talks to: booking its own position from fills, in the instrument's currency, and driving its StrategySignal, StrategyExecution and Order Manager with what the Event Loop delivers — stepping the signal on each bar, passing the bar on to StrategyExecution, and deciding when the signal may be rebuilt (only while flat with no open or submitted orders).
Not its jobIts params (StrategySignal holds them); the calculations and entry/exit logic (StrategySignal); which execution phase the slot is in or what an order event means in it (StrategyExecution); an order's life from submission to closed status (Order Manager); when bars are complete (Event Loop).
ReceivesFrom the Event Loop: completed bars, order updates and warmup history. From Aux Data (proposed): ready / not ready and history frames. From outside: deployment config. From StrategySignal: warm/not-warm. From StrategyExecution: whether it is processing an order. From Order Manager: ownership answers.
ProducesTo StrategySignal: bars with position data (entry price, seconds since entry) and rebuild requests. To StrategyExecution: bars and order updates. To Order Manager: order updates and ownership checks.

StrategySignal

OwnsThe slot's signal: its calculation DAG and params, stepping the calculations on each bar in dependency order, evaluating the entry and exit logic, reporting whether it is warm, and how to rebuild itself cold by replaying seed bars. Written as a Python SignalDag subclass that holds its own params (decision 42).
Not its jobWhen it is stepped or rebuilt (Strategy); the position or fills beyond what Strategy passes in (Strategy); acting on its signals, or when its exit inputs are frozen and released (StrategyExecution); orders (Order Manager); talking to the Event Loop (Strategy).
ReceivesFrom Strategy: bars with position data, and rebuild requests. From StrategyExecution: entry/exit questions and exit-input freeze/release.
ProducesTo StrategyExecution: entry/exit signals. To Strategy: warm/not-warm.

StrategyExecution

OwnsThe slot's execution state machine: which phase it is in, when to enter and exit by asking the slot's signal, and what each order event means in the current phase.
Not its jobThe signal's logic or when it is stepped (StrategySignal, Strategy); the position (Strategy); an order's life at the broker (Order Manager); talking to the Event Loop (Strategy).
ReceivesFrom Strategy: bars and order updates. From StrategySignal: entry/exit signals. From Order Manager: answers about its orders (status and filled quantity, submitted and open orders, group finality).
ProducesTo Order Manager: entry and exit orders, cancels, and order queries. To StrategySignal: entry/exit questions and exit-input freeze/release. To Strategy: its phase, through query answers.

Order Manager

OwnsThe life of every order the slot sends: building it, tracking it from submission to a closed status, knowing which orders the slot owns, and sending cancels.
Not its jobDeciding to enter or exit (StrategyExecution); the position (Strategy); broker communication (Gateway).
ReceivesFrom StrategyExecution: entry and exit orders, cancels, and order queries. From Strategy: order updates and ownership checks.
ProducesTo Gateway: orders and cancels. To Strategy: ownership answers. To StrategyExecution: query answers (its submitted and open orders, group finality, filled quantities).

Safety

OwnsDetecting a lost broker connection or a frozen process, reconnecting, and un-sticking any strategy left waiting on an order whose fill happened during the outage.
Not its jobTalking to the broker itself (Gateway); deciding what to trade (Strategy, StrategyExecution); normal event delivery (Event Loop).
ReceivesFrom Gateway: connection health and the broker's executions.
ProducesTo Gateway: heartbeat checks and reconnect requests. To the Event Loop: repaired fill events.

Shared, owned by no component

  • Exchange profiles — one per exchange: sessions, calendar, venue, currency, contract identity and, for futures, roll (decision 31).
  • Instruments — asset class, symbol, exchange profile, currency, multiplier, tick size (decision 37, 41).
  • Configuration loading and structured logging.
  • Proposed (decision 46): Clock — now() and wait(timeout), as WallClock or ReplayClock; and RunMode — the run mode, built once by the runner.

Open questions · not decided

QuestionWhere it stands
How is an option contract picked?An option instrument needs an expiry, a strike and a right (call or put), and option contracts expire. Who picks them — fixed in deployment config, a selection rule like the futures roll rule, or the strategy at entry from an option chain — is not decided. The last one would bring option-chain data into the boundary (decision 41).
Is the broker timestamp precise enough?R3's 5 ms starts at the closing tick's broker timestamp. If the broker stamps ticks only to the second, or its clock is not in step with ours, the number cannot be measured to 5 ms. How the start time is taken, and how clock offset is handled, is not decided (decision 25).
Bars closed without a tick?A bar can also be closed by the flush timer after its grace (1.0 s) when no tick arrives. Such a bar has no closing tick, so whether it counts toward the 5 ms budget, and from what start, is not decided.
Size beyond 1 unit?Decision 24 keeps every entry at 1 unit (1 share, or 1 contract). Stock books in particular may want larger sizes; changing it reopens partial fills everywhere.
System map · Golden sample · frozen

Golden sample · frozen

Input

A few minutes of synthetic 1-second ticks entering through the Gateway in replay mode, run with a trivial fixed-rule strategy: go long 1 contract once on the first bar closing above a fixed level L, and exit on the first bar reaching a fixed target T. The price path rises through L, later reaches T, and there is no connection outage.

It is small because it is a few minutes of hand-made prices. Its known answer is exactly one buy on the L-cross bar and one sell on the T bar.

Per component

ComponentExpected behaviour
GatewayDelivers every tick of the session in order, followed by end of data; accepts exactly two orders and returns a fill for each.
Event LoopDelivers each completed 1-second bar to the strategy exactly once, in time order; delivers both fills; stops after the data ends.
StrategySteps the signal on every bar and passes every bar and both fills on; books a long 1 position on the buy fill and flat on the sell fill; ends flat.
StrategySignalIs warm from the first bar; entry true only on the L-cross bar; exit true on the T bar.
StrategyExecutionStays flat until the L-cross bar and decides one buy; moves to in-position on its fill; decides one sell on the T bar; returns to flat on its fill and decides nothing afterwards.
Order ManagerSubmits exactly two market orders, tracks each to filled, and ends with no open or submitted order.
SafetyRequests no reconnect and repairs nothing.
Aux Data (proposed)The strategy reads no auxiliary name: reads no source, arms nothing, adds nothing to any bar.

End to end

The broker receives exactly one buy and one sell of 1 contract, on the L-cross bar and the T bar, and the book ends flat.

Decisions already made

Goal and boundary

1What is the system's one goal?

Execute a strategy book at the broker, placing the same orders on a simulated broker, a paper account or a live account.

2Who consumes the output?

The broker only.

3Are strategy research, comparing results with research, a strategy/params registry or decay monitoring inside the boundary?

None of them. None of that work happens here, so they are left out of the map.

4How many components?

Seven: Gateway, Event Loop, Strategy, StrategySignal, StrategyExecution, Order Manager, Safety.

Rejected: folding Safety into Gateway (it fails and recovers independently of trading); a separate Warmup component (not needed at this level).

proposed change: eight, with Aux Data (decision 44)

5Where do strategy params and deployment config sit?

Deployment config is an external input, not a component. Strategy params sit inside each strategy's signal class (decision 42): they are code the strategy author writes, not config.

Rejected: a Configuration component (the engine reads config, it does not own it); params in outside config (a second place that must agree with the code).

changed 2026-11-07 · params were an external input

6How do simulation/replay modes relate to the boundary?

A swap behind the Gateway: a simulated broker that replays data and fills orders sits behind the same interface as the real one, so every other component runs unchanged.

Rejected: a separate Simulator component, a simulation path that feeds strategies directly, and leaving sim out.

7The broker is both source and sink — one Gateway, or split feed/orders?

Keep one Gateway per broker, serving every instrument the process trades there. The diagram's order arrow is labelled as leaving through the Gateway.

Rejected: a Market Feed / Order Router split.

8What does Safety exchange?

Heartbeat and reconnect with Gateway, executions from Gateway, repaired fill events into the Event Loop.

Rejected: detection-only.

Splitting the slot

14Why split StrategyExecution and Order Manager out of Strategy?

Separation of work: Order Manager handles the order lifecycle, StrategyExecution handles the execution state machine, and Strategy is the higher-level object that uses both to interact with the Event Loop and consume its updates.

Resting broker-side exits (OCA groups) made both concerns the hard part.

15Who talks to Order Manager?

Both: StrategyExecution sends entry and exit orders and cancels and queries its own orders; Strategy forwards order updates and checks ownership.

Rejected: routing everything through StrategyExecution, and Strategy relaying Order Manager's answers to StrategyExecution in an order-context object.

16Who owns the position?

Strategy.

Rejected: moving it into Order Manager.

17Does the golden sample change with the split?

No: the same bar-close round trip, with expected behaviour for StrategyExecution and Order Manager.

Rejected: a resting-exit sample.

18Does the system's goal or external boundary change with the split?

No; only the internal split changes.

19Why split StrategySignal out of Strategy?

It is deterministic (bars and position data in, entry/exit answers out, no I/O), and it is where most warmup and signal bugs live; giving it its own boundary lets it be tested alone, from bars in to answers out. Strategy becomes the driver of StrategySignal, StrategyExecution and Order Manager, and stays the only component the Event Loop talks to.

20Who calls the signal?

Strategy and StrategyExecution: Strategy steps StrategySignal on each bar and rebuilds it; StrategyExecution asks it for the entry or exit answer in the phase that needs one. The Event Loop never reads the signal; it goes through Strategy.

Rejected: Strategy evaluating both answers and handing them to StrategyExecution — evaluating exit while flat, or entry before warmup, reads calculations that do not exist yet, and choosing by phase would leak the state machine into Strategy.

21Does the signal see more than bars?

Yes, position data: Strategy passes strategy data (entry price, seconds since entry) into each step, and StrategyExecution times the exit-input freeze (entry-decision bar) and release (flat again). The signal never reads Strategy's position itself. It answers exit per condition as well as overall, so StrategyExecution can mask conditions a resting broker order already covers.

22Who owns the signal rebuild (cold reset + seed replay)?

Split: StrategySignal owns how; Strategy owns when — only while flat with no open or submitted orders, which needs position and Order Manager state the signal must not see.

23Who seeds strategies with warmup history (fetch, retry, auxiliary data)?

The Event Loop. It already holds the per-instrument plumbing and the loop the retries run on; Strategy decides only when a rebuild may happen (decision 22) and the signal how. Still no separate Warmup component (decision 4).

proposed change: auxiliary data moves to Aux Data (decision 44); broker history stays here

24What size does a slot trade?

Always 1 unit per entry: 1 contract for futures and options, 1 share for stocks. So an order fills whole or not at all: partially filled orders and partial exits are not handled anywhere (Order Manager, StrategyExecution, Safety's repair), and a design or review must not raise them as a gap. Changing the size reopens this decision.

carried · wording widened from "1 contract" to "1 unit" for stocks and options, 2026-11-06

Latency and concurrency (R3)

25What latency does R3 measure?

The 5 ms budget is end-to-end latency: from the broker timestamp of the tick that closes a bar to that bar's order leaving the Gateway for the broker, at p99. It is logged per minute as p50/p99 together with its two internal parts: slot cost (one strategy, one bar) and dispatch latency (a bar's closing event entering the event buffer → the last strategy on that instrument done). Because feed transit counts against the budget, the engine's own share is what is left after transit.

Rejected: bar age measured from the bar's nominal end time — it includes the wait for the next tick that closes the bar (often hundreds of ms in a quiet market), which no engine design can remove. Rejected: counting only internal processing (slot cost or dispatch latency alone) — the budget is from the broker's time to the order.

proposed

26How does the Event Loop learn there is work?

A drain wake-up: every producer of the event buffer raises it after appending (the broker's reader thread through a thread-safe call into the loop), and the loop waits on it with a timeout equal to the bar-flush cadence (20 ms), so the clock-driven bar flush still runs on time. The event buffer stays a deque. This removes a 0–20 ms queue wait on every event that a fixed polling timer would add. A producer raises the wake-up only when none is pending, the buffer drains a control lane before a data lane, and each pass has a batch budget (Event Loop decision 8).

Rejected: a shorter timer (more idle wake-ups and still a floor); an asyncio queue everywhere (replay preloads the whole day into the buffer and puts fills at its front).

proposed

27What happens when the event buffer backs up?

It stays lossless (order updates are never dropped), but a backlog over a threshold becomes an ERROR with an operator alert, and its size and the queue wait are logged with each drain pass.

Rejected: a hard size limit that drops events — it could drop a fill.

proposed

28What concurrency model runs the strategies?

One process, one asyncio event loop, the broker's reader thread and one send thread; strategies on a bar are stepped one after another, in time order. One process keeps dispatch latency under 5 ms at p99 up to about 10 strategies active at once; under R3's end-to-end budget the engine's share is 5 ms less feed transit, so that count is an upper bound to be re-measured. The load target is 3 tick-by-tick streams and 10–15 strategies; whether one process carries it is decided by a measured scale trigger, not by a strategy count (Event Loop decision 9). Beyond that, split into process shards by strategy group, with one process still owning the single Gateway (decision 7 holds). Before sharding, Safety and its repair need a design that covers every shard.

Rejected: a thread per strategy (the GIL serialises CPU-bound Python anyway); an asyncio task per strategy (no parallelism, and the time-order guarantee gets harder to keep); one actor per strategy and gateway with message ports between them (no global time order, and ports wired by hand); sharding before it is needed.

proposed

29Where are per-bar logs written?

Off the loop thread: loggers hand records to a queue and a listener thread writes the files. Record content and field names are a stable format that outside tools may read.

Rejected: dropping per-bar indicator logs to DEBUG — they are how a run is audited afterwards.

proposed

33How is slot cost brought down before sharding?

Profile one strategy's bar first: logging is a small part of slot cost, so the rest is signal stepping and the execution state machine. Then consider computing a calculation once for all strategies on the same instrument when its registry name and params are identical. That would change who owns a calculation's state, so it needs its own decision first. This reduces sharding but does not replace it.

proposed

Extensibility (R2)

30What is the Gateway interface?

An abstract interface. Required methods have no body, so a gateway that misses one fails when it is built instead of returning nothing. Optional methods are gateway capabilities declared on the interface with safe defaults, never looked up by name at runtime. Gateways are picked by name from a registry. History is requested in broker-neutral units (months or dates), not broker-specific duration strings. See Gateway.

Rejected: splitting the Gateway (decision 7 holds).

proposed

31Where do exchange facts live?

In one exchange profile per exchange, in shared code: session names, calendar and early closes, the continuous data session, contract venue and currency, the broker's contract identity, the futures contract roll rule and session-end cutoffs. Every component reads it; no other file branches on an exchange name. CME and Eurex are the first two profiles.

Rejected: one component owning the calendar — the Event Loop, Gateway, Safety and StrategySignal all read it; special cases for one exchange spread over the files that need them.

proposed

32How do auxiliary data sources plug in?

Outside data sources are named on the boundary as a second external input, read only by Aux Data (decision 44), each through one data-source interface. A new feed or backup is one new class.

Rejected: moving them behind the Gateway — the Gateway is the broker only (decision 7).

proposed · changed 2026-11-07 · was the Event Loop's auxiliary data provider

Add a strategy without a restart (R5)

34Who owns the set of strategies the process runs?

The Event Loop, as one runtime book: strategies in dispatch order, per-instrument resamplers and bar buffers, contracts, the recording session maps and the background retry tasks. Only the drain-loop task changes it, and only at a commit boundary: another task hands it a book operation and awaits the result, so a bar or order dispatch already in flight never sees the book change. Everyone else reads membership from the book at call time — shutdown, Safety's repair and positions poll, the auxiliary retry, the recorders and the reconnect resubscribe — so a strategy added later is a full member. Cold start and hot-add go through the same steps: reserve instruments, stage, prepare, commit.

Rejected: each consumer keeping its own copy of the strategy list made at start; a book changed from any task (a dispatch could see a half-added strategy).

proposed

35How does an operator add a strategy to a running process?

A separate client script, deploy_strategy.py --config FILE --key KEY. It reads the same config file to find the socket and the sha256, sends one request and exits with the terminal status. The runner, in paper and live only, listens on a local socket next to its logs (directory 0700, socket 0600). One deploy request per connection names one strategy key and the config file's sha256; the runner streams status lines (preparing, then one of registered, noop, rejected, failed) with a reason and the revision (the config file's sha256). Which version of a strategy's code runs is not tracked: version control of strategies is outside the system. Requests run one at a time. Every terminal status is logged with the same hash fields as the startup deploy fingerprint. The slot is first added to the config file, so the next cold start runs it too: the deploy request is the existing deployment-config input arriving while the process runs (decision 5 holds). Simulation never opens the socket.

Rejected: a --deploy flag on the runner script (a short socket client and the long-running driver would share one parser and one main); a second service; the runner polling the config file.

proposed · changed 2026-11-07 · was a --deploy KEY flag on the runner script

36What may a deploy request do?

Add one new strategy key, nothing else, and only when it cannot disturb what is running. It is refused, before anything is touched, when the config differs anywhere but the new slot (config_drift), the key already runs (conflict), the strategy's session is open (session_open), its next session closes after this process exits (after_process_exit), no running strategy uses its account (unknown_account_route), or a position or order on its execution instrument belongs to no running strategy, compared per account (unmanaged_exposure; nothing is cancelled or flattened). A failure after that cleans only what the candidate created; shared feeds and running strategies are never touched. A committed strategy starts gated and can first enter at its next session open, once warmup and auxiliary data are ready.

Rejected as out of scope: changing or removing a running strategy, reloading code or params, starting a strategy inside its own session, adding several strategies atomically, new account routes, changing when the process exits, automatic recovery from quarantine.

proposed

Multi-asset and multi-currency (R1)

37What is an instrument?

One shared value naming a tradable product: its asset class (decision 41), symbol (NQ, ES, FDAX), its exchange profile, its currency, multiplier (1 for a stock) and tick size. Every tick, bar, order, fill and position carries the instrument, so no component needs to guess an exchange or a currency from a symbol. For a future, the front-month contract is resolved from the instrument by its exchange profile's roll rule; a stock is its one listing and has no roll; how an option contract is resolved is an open question.

proposed · v3

38How does a strategy name what it trades?

By two instrument lists in its deployment config: signal instruments (market data it subscribes to) and execution instruments (where its orders and position live). They are usually the same; they differ when a strategy reads one market and trades another.

39What currency is money counted in?

Every money amount carries its currency, and Strategy books position and PnL in its execution instrument's currency (USD for NQ/ES, EUR for FDAX). The engine never converts between currencies; account cash per currency is read from the broker. Reporting a book in one base currency is outside the system.

Rejected: converting to a base currency inside the engine (it needs a live FX rate source on the trading path, and no trading decision needs it).

40Do sessions differ per instrument?

Yes. StrategySignal model

42How is a StrategySignal written?

As a Python SignalDag subclass, registered by name. It declares its params as a typed, frozen dataclass whose defaults are the values, and builds its DAG in build_graph() from registered calculations, inline Python expressions, named conditions and named exits. The SignalDag base class implements the whole abstract signal interface, so a strategy author writes only the params and the graph. The instrument comes from deployment config and the session from the exchange profile. See StrategySignal.

Rejected: a declarative signal definition file (a second format to parse and check; a Python class is checked at import and build); params in outside config (decision 5); shipping the interface only (every user would have to bring a signal layer).

Custom strategies

43How does the engine load a custom strategy?

run_strategies.py is the only entry point that runs strategies. At start it imports every folder under local/strategies/ by file path: calculations.py, strategy_signal.py and strategy.py. The three files do not import from each other; they connect by registry names. register_calc binds a calculation in its folder's scope; register_signal_dag and register_strategy bind global names. A slot's config names its strat (the registered strategy name); the strategy names its signal; the signal's graph names its calculations, looked up in the folder's scope first and then in the built-in library. Lookups run when a slot is built, after every import, so import order does not matter. A name bound twice in the same scope stops startup and names both files.

Rejected: imports between the files of a strategy folder (the folder is not a package on the engine's import path); one global calculation namespace (two folders could not each have their own rsi).

44Is auxiliary data its own component?

Yes: Aux Data, the eighth component. It has its own outside input, its own failure modes (source down, value not settled, provisional value changed, backup not confirmed) and its own clock (arming by each session's open, on each exchange's clock). It meets the rest of the engine at three points only: values on a bar (called by the Event Loop before dispatch), frames for a cold rebuild (read by Strategy), and ready / not ready (sent to Strategy). A group's arm session comes from the exchange profile. Once confirmed, decision 4 reads "eight" and decision 23 keeps only broker history in the Event Loop.

Rejected: keeping it in the Event Loop (its widest part, with most of its outside I/O); behind the Gateway (decision 7); a component for resampling too (a small pure module with no outside input; see the Event Loop map, decision 7).

45Who prepares replay data?

The simulated broker, on request (Gateway behaviour 15). It reads the tape lazily, checks it against the session from the exchange profile with one generic check, and answers daily-history and prior-session requests like the broker gateway. Padding and synthetic tapes are simulated broker options. The Gateway builds daily bars in live and replay; the Event Loop only requests them. This follows decision 6.

Rejected: the runner slicing the tape and writing history files before start (a second history path that must read strategies before they exist); one hand-written session check per exchange.

46How do components differ between replay and live?

Only through what the runner passes in. A shared Clock (now(), wait(timeout)) is a WallClock live and a ReplayClock in replay, moving forward on each bar close; the bar flush, session-end flatten, reconcile and the session-active flag read it. RunMode is built once by the runner, which uses it to choose components and do-nothing stand-ins (recorders, Safety, state stores). No component reads the mode or checks a collaborator for None.

Rejected: checking a mode string inside components (it spreads, and a check that matches the wrong mode runs the wall clock against replayed data).

47What does run_strategies.py do?

It is a thin startup module. It parses --config and --mode only (the deploy client is deploy_strategy.py, decision 35); replay settings (tape, date, session) sit in a replay: section of the config. It builds a Runtime from the config and the mode: the gateway by registry name (decision 30), the clock, the stand-ins and each component with its own typed config section. Every long-lived part follows one Service protocol (start(), stop()); Runtime starts them in order and stops them in reverse, also when start-up fails, then runs the Event Loop. Logging is one queue-handler setup (decision 29) with a logger per module. Comparing results with research stays outside (decision 3).

async def main(cfg, mode):
    async with Runtime.build(cfg, mode) as rt:
        await rt.run()

Rejected: building components one by one with a try/finally of None checks; a long list of replay flags on the command line; keyword arguments copied one by one from config into a component.
