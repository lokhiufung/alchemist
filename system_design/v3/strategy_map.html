Strategy

The one object per slot that the Event Loop talks to. It drives the slot's three parts — StrategySignal, StrategyExecution and Order Manager — with what the Event Loop delivers, and books the slot's own position from fills.

v3 draft, 2026-11-06 — not agreed. Behaviours and decisions are settled. The calls Strategy makes on StrategySignal use the v3 signal interface (StrategySignal skeleton). Multi-asset: the position is booked in the execution instrument's currency (System map decision 39). 2026-11-07: the strategy is registered with register_strategy and names its signal by registry name; the signal is built with from_config() and its params sit in the signal class; logs and snapshots read values() (decision 16).

Strategy · What this component does

What this component does

On each bar

Strategy is the only thing that steps the slot's StrategySignal. It steps it once with step(), passing strategy data built from its position:

  • entry_price — the booked average price;
  • secs_since_entry — counted from the entry-order bar.

Both are None while flat. It then passes the bar to StrategyExecution, which asks the signal for the entry or exit answer its phase needs, decides, and sends orders through Order Manager.

On each order update

It forwards the update to Order Manager, books the position only from the change Order Manager returns, and passes the update to StrategyExecution — which asks Order Manager itself for anything more it needs. The new entry price reaches the signal through strategy data on the next bar.

When late data arrives

When late warmup or auxiliary data arrives, it rebuilds the signal cold — but only while is_flat_idle() holds: no position, and Order Manager has no open or submitted order. Then it tells StrategyExecution the slot is ready.

Sample

Strategy's slice of the system golden sample from the System map.

InputA synthetic price path that rises through fixed level L on bar 10 and later reaches target T on bar 20, with no outage. A fixed-rule long signal: entry true on the first close above L, exit true on the first bar reaching T. StrategySignal and StrategyExecution are scripted stubs; Order Manager is a mock that returns each fill as an owned change.
ExpectedStrategy steps the signal exactly once per bar, before StrategyExecution sees that bar. On the buy fill it books +1, and from the next bar steps the signal with entry_price = fill price. On the sell fill it books 0. It ends flat with entry_price back to None.
Passes whenEvery bar reaches the signal once and StrategyExecution once, in that order; the position is +1 between the two fills and 0 at the end.

Strategy · Behaviours

Behaviours

Each behaviour says what Strategy is given, what it must do, and what must always stay true.

1Bar drive

Given
A completed bar from the Event Loop.
Must
Call StrategyExecution's on_bar(bar, step_signal). When it calls step_signal, call the signal's step() with the bar history and strategy data from the booked position.
Invariant
The signal is stepped exactly once per in-session bar, and before StrategyExecution sees that bar. The first in-session bar is the session's bar 0, so no step happens while StrategyExecution waits for the session, or while a quarantined slot is out of session.

2Exit-input freeze and release timing — not a Strategy behaviour

StrategyExecution calls freeze_exit_inputs() / release_exit_inputs() (StrategyExecution behaviour 1). The number is kept so references to the later behaviours stay valid.

3Order-update relay and position booking

Given
An order update from the Event Loop.
Must
  • Forward it to Order Manager. If Order Manager returns no change, stop.
  • Otherwise book the position (size, average price, currency, entry timestamp = the entry-order bar) from the returned change, and call StrategyExecution's on_order_update(order_update).
  • Also: build Order Manager with the slot's account; apply a broker position update only for this slot's execution instrument; take in a balance update for this slot's account and its instrument's currency.
Invariant
The position changes only from changes Order Manager returns, each booked once. The signal sees position data only through strategy data.

4Readiness and rebuild timing

Given
Warmup history from the Event Loop, or auxiliary ready / not ready with its frames from Aux Data (proposed, System map decision 44), or the signal not yet warm. On a cold rebuild while aux is ready, Strategy reads the frames again from Aux Data.
Must
  • Rebuild the signal cold and replay the seed bars only while is_flat_idle() holds (no position, and Order Manager has no open or submitted order); then set StrategyExecution's warmup-ready / aux-ready.
  • During a mid-session replay, hold live bars back and step them afterwards, in order. Replayed bars outside the slot's session are skipped.
Invariant
No rebuild ever happens with a position or an open or submitted order. StrategyExecution is never told "ready" while the signal is not warm. No live bar is stepped in the middle of a replay or dropped by it.

5Teardown

Given
A request_flatten call (session end, shutdown) — or Strategy's own call with reason exit_failed, made on each bar while StrategyExecution reports flatten_wanted() after an exit failed in position (StrategyExecution behaviour 12).
Must
Hand StrategyExecution the booked position on every call. StrategyExecution cancels every order, waits until each is final, then sends one market order opposite the booked position (none when flat) and goes to DONE (StrategyExecution behaviour 11). is_flat_idle() counts submitted, open and cancelling orders.
Invariant
A flat slot sends no close order.

6Signal state across a restart

Given
A state store and the signal's list of values fixed for the session.
Must
Accept only session-fixed values as cached. Once warm, persist their state once. On restart, restore it (logging loudly), and treat a missing or corrupt record as nothing to restore. A quarantined slot never persists.
Invariant
Only values that cannot go stale while the process is down are restored.

7Observability

Given
A snapshot interval and the slot's health.
Must
Log a signal snapshot, built from the signal's values(), every N bars (never when 0) with instrument and event fields. Mark a quarantined slot's in-session snapshot row as stale; a healthy row carries no stale keys. The write happens on a logging thread, not the event loop (System map decision 29).
Invariant
Logging never changes what is traded.

"""Skeleton contract for Strategy, the slot driver (Alchemist v3, draft)."""

from __future__ import annotations

from collections import deque
from typing import Any

from alchemist.instruments import Instrument
from alchemist.strategy_builder.strategy_signal import StrategySignal
from alchemist.strategy_builder.strategy_executions import make_execution
from alchemist.managers.order_manager import OrderManager


class Strategy:
    name: str
    config: dict
    signal_instrument: Instrument
    execution_instrument: Instrument
    session: str
    position: dict          # size, avg_price, last_price, currency, entry_ts, side
    balance: dict           # {'currency': str, 'available': float | None}
    signal: StrategySignal
    signal_name: str        # registry name of the signal, set by the strategy subclass
    om: OrderManager
    execution: Any          # StrategyExecution, built by make_execution(config)
    deferred_bars: list | None

    # Behaviour 1
    def on_bar(self, bars: deque, bar: dict) -> None:
        """execution.on_bar(bar, step_signal); step_signal calls
        signal.step(bars, self.strategy_data()) exactly once."""

    def strategy_data(self) -> dict:
        """{'entry_price': ..., 'secs_since_entry': ...}; both None while flat."""

    # Behaviour 3
    def on_order_update(self, update: dict) -> None:
        """change = om.on_order_update(update); book only from change;
        then execution.on_order_update(update)."""

    def on_position_update(self, update: dict) -> None: ...
    def on_balance_update(self, update: dict) -> None: ...

    # Behaviour 4
    def warmup_requirements(self) -> dict:
        """Route the signal's declared history needs to the Event Loop."""
    def warmup(self, history: dict) -> None: ...
    def rebuild_intraday_state(self, seed_bars: list) -> None: ...
    def reset_signal(self) -> None:
        """self.signal = get_signal_dag(self.signal_name).from_config(self.config)."""
    def is_flat_idle(self) -> bool:
        """No position; no submitted, open or cancelling order."""

    # Behaviour 5
    def request_flatten(self, reason: str, bar_ts: float) -> None: ...

    # Behaviour 6-7
    def restore_signal_state(self) -> None: ...
    def signal_snapshot(self) -> dict: ...

    # Slot-state routing (decision 14)
    def is_processing_order(self) -> bool: ...
    def quarantine(self, reason: str) -> None: ...
    def is_quarantined(self) -> bool: ...
    def get_submitted_orders(self) -> list: ...
    def get_open_orders(self) -> list: ...
    def get_cancelling_orders(self) -> list: ...

Strategy · Decisions already made

Decisions already made

1Who drives the signal?

Strategy steps and rebuilds it; StrategyExecution holds it and asks it for the entry/exit answers (System map decision 20).

Rejected: Strategy evaluating the answers and handing them over.

2What does Strategy need from the signal's interface?

Step, warm state, rebuild, warmup requirements, and the entry/exit answers StrategyExecution asks for — including per-condition exit answers and each exit condition's level, so a protected slot can rest a broker order at the level the signal already computes — and the read-only values() for logs and snapshots.

Rejected: skip-masks or a fill callback inside the signal.

3How does the signal see position data?

Through strategy data (entry price, seconds since entry) passed into each step (System map decision 21). It never reads the position itself.

4Who freezes and releases the signal's exit inputs?

StrategyExecution: freeze on the entry-decision bar before the entry order is sent; release on the exit fill or when the entry dies.

Rejected: moving them to Strategy.

5Who owns the rebuild?

Split (System map decision 22): StrategySignal owns how; Strategy owns when (flat, idle, no open or submitted order).

6Where do session gating, entry/exit placement, quota and teardown live?

In StrategyExecution (its own map). StrategyExecution reads the params it needs through the signal it holds.

7Fill attribution

Strategy books only what Order Manager returns as a change (Order Manager owns ownership).

8What anchors the entry timestamp?

The bar that submitted the entry.

9Does Strategy relay Order Manager's answers to StrategyExecution?

No. Strategy passes the order update on as is; StrategyExecution queries Order Manager itself.

Rejected: an order-context relay — it duplicated the open and submitted orders Order Manager already stores.

10How does the Event Loop's warmup seeding reach the signal?

Through Strategy only: warmup_requirements() and warmup() route to the signal; the Event Loop never reads the signal.

11Who logs the entry/exit decision's inputs?

StrategyExecution, when it evaluates the signal.

14How does code outside the slot ask about it?

Only through Strategy: is_processing_order() forwards to StrategyExecution; get_submitted_orders() / get_open_orders() / get_cancelling_orders() forward to Order Manager under its own status names; is_flat_idle() is answered here; is_quarantined() too. Safety's repair picks slots by their submitted and open orders.

Rejected: names that are not order statuses ("pending", "working").

15An unknown key in a slot's config?

Logged, never fatal. A bad execution block fails startup (StrategyExecution decision 21).

16How is a strategy declared, and how is its signal built?

A strategy is a small declarative subclass in its folder's strategy.py, registered with register_strategy(strat); the slot config names that strat. It names its signal by registry name (signal_name), not by import (System map decision 43). Strategy builds the signal with get_signal_dag(signal_name).from_config(config) at start and on every rebuild, and reads it only through the public signal interface (StrategySignal decision 8).

Rejected: reading or writing the signal's value cache directly for logs or restore.
