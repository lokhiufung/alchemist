Strategy · 1 · Goal and scope

Goal and scope

What it is. Strategy is the one object per slot that the Event Loop talks to. Strategy drives the slot's three parts (StrategySignal, StrategyExecution and Order Manager) with what the Event Loop delivers, and books the slot's own position from fills. A strategy author registers a strategy class and names its signal by registry name (decision 16).

Why it exists. The Event Loop must see one interface per slot, not three parts. The three parts must not reach into each other: the signal must not read the position, and StrategyExecution must not decide when a signal may be rebuilt. Strategy holds the position and the slot's timing rules (when to step the signal, when a rebuild is safe), so each part stays testable alone (System map decisions 19, 22).

Goal. Be the one per-slot object the Event Loop talks to, and drive StrategySignal, StrategyExecution and Order Manager with what the Event Loop delivers, booking the slot's own position from fills.

Features

Algorithm map

Feature cards

1The signal is stepped once per bar, before the decisionsettled · was behaviour 1 · decisions 1, 3

Need
StrategyExecution asks the signal for an entry or exit answer on each bar, so the signal must already include that bar. The signal also needs position data (entry price, seconds since entry) without reading the position itself.
Upstream gives
The Event Loop delivers each completed bar once, in time order (Event Loop feature 2). StrategyExecution knows whether the bar is in session.
Algorithm
  1. Pass the bar to StrategyExecution together with a step-signal callback.
  2. When StrategyExecution calls the callback, build strategy data from the booked position: entry price = booked average price; seconds since entry = counted from the entry-order bar. Both are None while flat.
  3. Call the signal's step with the bar history and the strategy data.
Parameters
None.
Invariant
The signal is stepped exactly once per in-session bar, before StrategyExecution decides on that bar. The first in-session bar is the session's bar 0; no step happens while StrategyExecution waits for the session, or while a quarantined slot is out of session.

2The position is booked only from Order Manager's changessettled · was behaviour 3 · decisions 7, 8, 9

Need
The slot's position must count each fill exactly once, in the execution instrument's currency, even though every slot sees every broker update.
Upstream gives
The Event Loop delivers every order, position and balance update to every slot (Event Loop feature 3). Order Manager returns a change only for an owned order, once per fill (Order Manager feature 3).
Algorithm
  1. Forward each order update to Order Manager. If Order Manager returns no change, stop.
  2. Book the position from the returned change: size, average price, currency, entry timestamp = the entry-order bar.
  3. Pass the update to StrategyExecution. StrategyExecution asks Order Manager itself for anything more it needs.
  4. Log a broker position update for this slot's execution instrument and account; never book the position from it, because several slots can share one account and instrument. Take a balance update only for this slot's account and the instrument's currency.
Parameters
ParameterConfigurable?SupportedDefault
Position currencyFixed per instrument (exchange profile, System map decision 39)USD (CME), EUR (Eurex)—
Invariant
The position changes only from changes Order Manager returns, each booked once. The signal sees position data only through strategy data.

3A rebuild happens only while flat and idlesettled · was behaviour 4 · decisions 5, 10

Need
Late warmup history or late auxiliary data means the signal must be rebuilt cold. A rebuild in the middle of a trade would change the exit logic under an open position.
Upstream gives
Warmup history from the Event Loop (Event Loop feature 7); ready or not ready with frames from Aux Data (Aux Data feature 4), and frames again on request during a rebuild (Aux Data feature 8); the signal's warm report.
Algorithm
  1. Rebuild only while flat and idle: no position, and Order Manager has no open or submitted order.
  2. When late warmup history or late aux frames arrive while the slot is not flat and idle: keep them as a pending rebuild (a newer value replaces an older one) and clear the matching ready flag at once, so the slot makes no new entry. The open trade keeps its current signal and its exits. Run the pending rebuild at the first moment the slot is flat and idle. A pending rebuild still waiting at session end is logged at WARNING (System map decision 53).
  3. Build the signal cold and replay the seed bars; then set StrategyExecution's warmup-ready, only when the Event Loop's seed state is READY and the signal reports warm (System map decision 52). Set aux-ready when Aux Data reports ready; when the signal reads no auxiliary name, set aux-ready once, when the slot is built.
  4. During a mid-session replay, hold live bars back and step them afterwards, in order. Skip replayed bars outside the slot's session.
Parameters
None.
Invariant
No rebuild happens with a position or with an open or submitted order. StrategyExecution is never told "ready" while the signal is not warm. No live bar is stepped in the middle of a replay or dropped by the replay.

4A flatten hands StrategyExecution the booked positionsettled · was behaviour 5 · decision 6

Need
At session end, at shutdown, or after an exit failed in position, the slot must close exactly the position Strategy booked, and a flat slot must send nothing.
Upstream gives
A flatten request from the Event Loop (Event Loop feature 8), or StrategyExecution reporting that a flatten is wanted after a failed exit.
Algorithm
  1. On each flatten request, hand StrategyExecution the booked position. On each bar while StrategyExecution reports that a flatten is wanted, call the flatten with reason exit_failed.
  2. StrategyExecution cancels every order, waits until each is final, sends one market order opposite the booked position (none when flat) and ends the day.
  3. Flat and idle counts submitted, open and cancelling orders.
Parameters
None.
Invariant
A flat slot sends no close order.

5Session-fixed signal values survive a restartsettled · was behaviour 6

Need
A process restart mid-session must not lose values fixed for the session (for example an opening range), because the history to rebuild those values may no longer be available.
Upstream gives
A state store, and the signal's list of values fixed for the session (StrategySignal).
Algorithm
  1. Accept only session-fixed values as cached.
  2. Once the signal is warm, persist their state once.
  3. On restart, restore the state and log loudly; treat a missing or corrupt record as nothing to restore.
  4. A quarantined slot never persists.
Parameters
None.
Invariant
Only values that cannot go stale while the process is down are restored.

6Signal snapshots are logged without touching tradingsettled · was behaviour 7 · System map decision 29

Need
A run must be auditable afterwards: the operator needs the signal's values next to each decision.
Upstream gives
The signal's values, and the slot's health (quarantined or not).
Algorithm
  1. Every N bars (never when N is 0), log a snapshot built from the signal's values, with instrument and event fields.
  2. Mark a quarantined slot's in-session snapshot row as stale; a healthy row carries no stale keys.
  3. Write the record on a logging thread, not on the Event Loop thread.
Parameters
ParameterConfigurable?SupportedDefault
Snapshot interval N (bars)Configurable per strategy (slot config)0 (off) or any positive count60 (once a minute at 1 s bars)
Invariant
For every N: logging never changes what is traded.

"""Skeleton contract for Strategy, the slot driver (Alchemist v3)."""

from __future__ import annotations

from collections import deque
from typing import Any

from alchemist.instruments import Instrument
from alchemist.strategy_builder.strategy_signal import StrategySignal
from alchemist.strategy_builder.strategy_executions import make_execution
from alchemist.managers.order_manager import OrderManager


class Strategy:
    name: str
    config: dict
    signal_instrument: Instrument
    execution_instrument: Instrument
    session: str
    position: dict          # size, avg_price, last_price, currency, entry_ts, side
    balance: dict           # {'currency': str, 'available': float | None}
    signal: StrategySignal
    signal_name: str        # registry name of the signal, set by the strategy subclass
    om: OrderManager
    execution: Any          # StrategyExecution, built by make_execution(config)
    deferred_bars: list | None

    # Behaviour 1
    def on_bar(self, bars: deque, bar: dict) -> None:
        """execution.on_bar(bar, step_signal); step_signal calls
        signal.step(bars, self.strategy_data()) exactly once."""

    def strategy_data(self) -> dict:
        """{'entry_price': ..., 'secs_since_entry': ...}; both None while flat."""

    # Behaviour 3
    def on_order_update(self, update: dict) -> None:
        """change = om.on_order_update(update); book only from change;
        then execution.on_order_update(update)."""

    def on_position_update(self, update: dict) -> None: ...
    def on_balance_update(self, update: dict) -> None: ...

    # Behaviour 4
    def warmup_requirements(self) -> dict:
        """Route the signal's declared history needs to the Event Loop."""
    def warmup(self, history: dict) -> None: ...
    def rebuild_intraday_state(self, seed_bars: list) -> None: ...
    def reset_signal(self) -> None:
        """self.signal = get_signal_dag(self.signal_name).from_config(self.config)."""
    def is_flat_idle(self) -> bool:
        """No position; no submitted, open or cancelling order."""

    # Behaviour 5
    def request_flatten(self, reason: str, bar_ts: float) -> None: ...

    # Behaviour 6-7
    def restore_signal_state(self) -> None: ...
    def signal_snapshot(self) -> dict: ...

    # Slot-state routing (decision 14)
    def is_processing_order(self) -> bool: ...
    def quarantine(self, reason: str) -> None: ...
    def is_quarantined(self) -> bool: ...
    def get_submitted_orders(self) -> list: ...
    def get_open_orders(self) -> list: ...
    def get_cancelling_orders(self) -> list: ...

Decisions already made

1Who drives the signal?

Strategy steps and rebuilds it; StrategyExecution holds it and asks it for the entry/exit answers (System map decision 20).

Rejected: Strategy evaluating the answers and handing them over.

2What does Strategy need from the signal's interface?

Step, warm state, rebuild, warmup requirements, and the entry/exit answers StrategyExecution asks for — including per-condition exit answers and each exit condition's level, so a protected slot can rest a broker order at the level the signal already computes — and the read-only values() for logs and snapshots.

Rejected: skip-masks or a fill callback inside the signal.

3How does the signal see position data?

Through strategy data (entry price, seconds since entry) passed into each step (System map decision 21). It never reads the position itself.

4Who freezes and releases the signal's exit inputs?

StrategyExecution: freeze on the entry-decision bar before the entry order is sent; release on the exit fill or when the entry dies.

Rejected: moving them to Strategy.

5Who owns the rebuild?

Split (System map decision 22): StrategySignal owns how; Strategy owns when (flat, idle, no open or submitted order).

6Where do session gating, entry/exit placement, quota and teardown live?

In StrategyExecution (its own map). StrategyExecution reads the params it needs through the signal it holds.

7Fill attribution

Strategy books only what Order Manager returns as a change (Order Manager owns ownership).

8What anchors the entry timestamp?

The bar that submitted the entry.

9Does Strategy relay Order Manager's answers to StrategyExecution?

No. Strategy passes the order update on as is; StrategyExecution queries Order Manager itself.

Rejected: an order-context relay — it duplicated the open and submitted orders Order Manager already stores.

10How does the Event Loop's warmup seeding reach the signal?

Through Strategy only: warmup_requirements() and warmup() route to the signal; the Event Loop never reads the signal.

11Who logs the entry/exit decision's inputs?

StrategyExecution, when it evaluates the signal.

14How does code outside the slot ask about it?

Only through Strategy: is_processing_order() forwards to StrategyExecution; get_submitted_orders() / get_open_orders() / get_cancelling_orders() forward to Order Manager under its own status names; is_flat_idle() is answered here; is_quarantined() too. Safety's repair picks slots by their submitted and open orders.

Rejected: names that are not order statuses ("pending", "working").

15An unknown key in a slot's config?

Logged, never fatal. A bad execution block fails startup (StrategyExecution decision 21).

16How is a strategy declared, and how is its signal built?

A strategy is a small declarative subclass in its folder's strategy.py, registered with register_strategy(strat); the slot config names that strat. It names its signal by registry name (signal_name), not by import (System map decision 43). Strategy builds the signal with get_signal_dag(signal_name).from_config(config) at start and on every rebuild, and reads it only through the public signal interface (StrategySignal decision 8).

Rejected: reading or writing the signal's value cache directly for logs or restore.
